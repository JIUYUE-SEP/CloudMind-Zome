# 看门狗调参指南

> 面向运维与二次开发：**要改哪个参数、改完有什么后果、怎么确认改对了**。
> 机制推导与设计取舍见 [`design/watchdog.md`](design/watchdog.md)，本文只讲操作。
> 最后核对：2026-11-05（对应 `plugins/watchdog`，P1–P4 全部已实施）

---

## 一、三层各管一种「不动」

出故障时先分清卡在哪一层，否则调错参数是白费。

| 层 | 判据 | 专治 | 配置位置 | 缺省 |
|---|---|---|---|---|
| **L0 流空闲** | 单次 provider 请求多久没收到任何数据 | 连接挂死、首 token 前无限静默 | `provider.requestTimeout`（ms）或环境变量 `CLOUDMIND_STREAM_IDLE_TIMEOUT_MS` | 180s |
| **L1 心跳** | 整个 turn 多久没有实质进展（完成一步 / 工具开始 / 工具结束） | 每步都在 L0 阈值内返回、累积卡很久的慢性卡死 | `settings.watchdog.stallThresholdMs` | 600s |
| **L2 语义** | 模型判断「最近的动作用没用」 | 动着但原地打转、反复读同一文件、早已跑偏 | `settings.watchdog.semanticReview` | **关闭** |

三者的关系是**互补而非递进**：

- L0 只看单次请求，一个 turn 每步都刚好在 179 秒返回，二十步卡一小时，L0 一次都不响；
- L1 补上这个空档，但它只看「有没有动」，反复读同一个文件的回合心跳一直很新鲜；
- L2 才问「动了有没有用」，代价是**要花一次模型调用**，所以缺省关。

把 L0 调小到 30s 并不能替代 L1：reasoning 模型思考阶段常静默一分钟以上，砍 L0 会大量误杀正常推理（这也是它缺省取 180s 的原因）。

## 二、参数总表

全部位于 `settings.watchdog`，经 `PUT /config` 写入（见 §四）。**所有字段可选**，缺席即缺省。

| 参数 | 缺省 | 合法值 | 调小的后果 | 调大的后果 |
|---|---|---|---|---|
| `enabled` | `true` | 布尔 | 关闭 L1 + L2（L0 不受影响） | —— |
| `stallThresholdMs` | `600000` | > 0 的整数 | 慢回合被误杀 | 真卡死要更久才自愈 |
| `scanIntervalMs` | `30000` | ≥ `5000`（1–4999 抬到 5000；0 或负数回缺省） | CPU 与日志变多 | 中断最多晚一个扫描周期 |
| `semanticReview.enabled` | `false` | 布尔 | 关闭 L2 | 按 §三 的节流开始产生模型调用 |
| `semanticReview.afterMs` | `stallThresholdMs / 2` | ≥ 0 的整数 | 更早开始审查（调用变多） | 只在临近硬杀时才审 |
| `semanticReview.cooldownMs` | `120000` | ≥ 0 的整数 | 同一 agent 审得更频繁 | 判过一次后长时间不再审 |

三条容易踩的规则：

1. **非法值一律回缺省，不会关闭看护**。`stallThresholdMs: 0`、`NaN`、`-1` 都按 600s 算——写错了最坏是「没按你想的调」，不是「看护静默失效」。（`scanIntervalMs` 同理会回 30s，不是抬到 5s。）
2. **`0` 在 `afterMs` / `cooldownMs` 上是合法值**，表示「不等待 / 不冷却」。只有负数和非数字才算没配。
3. **`afterMs` 的缺省是算出来的**。把 `stallThresholdMs` 改成 900s，`afterMs` 的缺省会自动变成 450s。想固定住就显式写。

`scanIntervalMs` 决定的是**发现延迟的下限**：卡死最坏要等 `stallThresholdMs + scanIntervalMs` 才被中断。30s 周期 + 600s 阈值 = 最坏 10 分半。

## 三、按症状查

| 症状 | 先确认 | 动作 |
|---|---|---|
| 回合卡住，要等十分钟才恢复 | `GET /system/watchdog` 里该回合的 `idleMs` 逼近 `thresholdMs` | 调小 `stallThresholdMs`；或把 `scanIntervalMs` 调到 10–15s 缩短发现延迟 |
| 正常长任务被中断，`aborted.reason` 是 `watchdog` | 当时是不是在跑 `run_command` / `dispatch_subagent` | 这些工具已自报上限，正常不该被杀；若跑的是**未声明 `timeoutMs`** 的工具（如 `generate_image`），给它补声明，或临时调大 `stallThresholdMs` |
| 回合明显在打转，却从没被中断 | `semanticReview.enabled` 是否为 `true`；快照里该回合有没有 `trace` | 开启语义审查，见 §四 |
| 开了语义审查后，长命令仍被杀 | 该工具的 `timeoutMs` 声明 | 自报时限内已自动跳过审查；没声明的工具没有「合法阻塞期」可依据，只能补声明或调大 `afterMs` |
| 开启后 token 消耗上升 | 审查频率 | 调大 `cooldownMs`（如 300000）、调大 `afterMs`；或确认审查走的是便宜模型（见下） |
| 中断了但不知道是谁干的 | `turn.end` 的 `aborted.reason` | `watchdog` = 心跳判定「根本不动」；`stalled` = 语义审查判「动着没用」；`user` = 手动停止 |

**审查用哪个模型**：按 `topicBoundaryModel` → `compressionModel` → `model` 降级。想压低成本，给 agent 配一个便宜的 `compressionModel` 即可，不必新增字段。审查单次超时固定 30s，超时按「仍在推进」放行。

## 四、写入配置

用 `PUT /config`，只传要改的字段——**逐字段合并，缺席保持原值**，`semanticReview` 也是嵌套合并，所以「先配冷却、后开开关」不会把冷却打回缺省。

```bash
TOKEN=$(cat "${CLOUDMIND_DATA_DIR:-$HOME/.cloudmind-zome}/auth-token")

# 只开 L1，并把阈值收紧到 5 分钟、扫描加快到 15 秒
curl -s -X PUT http://127.0.0.1:8848/config \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"watchdog":{"stallThresholdMs":300000,"scanIntervalMs":15000}}'

# 开启语义审查：停滞 4 分钟后开始审，审过一轮冷却 5 分钟
curl -s -X PUT http://127.0.0.1:8848/config \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"watchdog":{"semanticReview":{"enabled":true,"afterMs":240000,"cooldownMs":300000}}}'

# 临时全关（排查「是不是看护杀的」时最直接的手段）
curl -s -X PUT http://127.0.0.1:8848/config \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"watchdog":{"enabled":false}}'
```

**即时生效**，不必重启：插件每轮扫描都重新读配置，`scanIntervalMs` 的改动也在下一轮排程时生效（不需要重启，但也不会立刻重排当前这一轮）。

接口只校验形状（对象/布尔/数字），**不校验取值范围**——归一在插件侧完成。所以 `PUT` 回显的是你写进去的原始值，而 `GET /system/watchdog` 回显的是**实际生效值**，两者不一致时以后者为准。

### 三种典型配置

| 场景 | 配置 | 理由 |
|---|---|---|
| 日常（缺省） | `{}` | L1 兜底，不产生额外成本；卡死十分钟自愈 |
| 交互优先 | `{"stallThresholdMs":180000,"scanIntervalMs":10000}` | 对话场景卡三分钟就难以忍受；代价是极慢的合法回合会被误杀 |
| 长任务为主 | `{"stallThresholdMs":1200000,"semanticReview":{"enabled":true,"afterMs":600000,"cooldownMs":600000}}` | 放宽硬杀，改用语义审查捞「真打转」；审查频率压到十分钟一次 |
| 排查期间 | `{"enabled":false}` | L0 仍生效；先确认问题不是看护造成的 |

## 五、确认改对了

### 快照

```bash
curl -s http://127.0.0.1:8848/system/watchdog -H "Authorization: Bearer $TOKEN"
```

```json
{
  "enabled": true,
  "scanIntervalMs": 30000,
  "stallThresholdMs": 600000,
  "semanticReview": { "enabled": false, "afterMs": 300000, "cooldownMs": 120000 },
  "turns": [
    {
      "agentId": "agt_01H...",
      "startedAt": "2026-11-01T02:10:00.000Z",
      "lastActivityAt": "2026-11-01T02:16:30.000Z",
      "idleMs": 245000,
      "thresholdMs": 660000,
      "stepCount": 7,
      "activeTool": { "name": "run_command", "timeoutMs": 600000 }
    }
  ]
}
```

读法：

- `idleMs` 对 `thresholdMs` —— 差多少就是还有多久被判死。**不要拿 `stallThresholdMs` 当参照**，工具在跑时 `thresholdMs` 已被放宽（上例 660000 = 600000 + 60s 宽限）。
- `semanticReview.afterMs` 与 `cooldownMs` 是**生效值**，能直接看出你的配置有没有被归一。
- `turns` 为空 = 当前没有任何回合在跑，不是「看护没工作」。
- 插件被摘除时返回 `enabled: false` 与空 `turns`，而非 404——404 会让人误以为接口不存在。

关于 `aborted.reason`：`watchdog`（心跳判死）与 `stalled`（语义判打转）要分开看。前者查网络/进程/工具是否真卡住；后者查 prompt 与工具反馈是不是让 agent 在原地绕。

### 日志

| 日志 | 含义 |
|---|---|
| `[watchdog] turn 停滞超阈值，已中断` | L1 动手，带 `idleMs` / `thresholdMs` / `stepCount` / `activeTool` |
| `[watchdog] 语义审查判定原地打转，已中断` | L2 动手，带判定的 `model` |
| `[watchdog] 语义审查判 STUCK，但审查期间已有新进展，放行` | 二次确认拦下了误杀——**这条出现频率高说明 `afterMs` 偏小** |
| `[watchdog] 进度裁判调用失败/超时（按仍在推进处理）` | 审查自身故障，回合未受影响；频繁出现说明模型或网络有问题 |
| `[watchdog] 进度裁判输出无法解析（按仍在推进处理）` | 模型没按格式回，可考虑换 `compressionModel` |
| `[watchdog] 扫描失败` | 看护自身异常，下一轮自动继续；连续出现需查配置或仓储 |

日志不含对话内容，只有结构字段（与审批审计同口径）。

## 六、常见误配

| 配置 | 实际后果 |
|---|---|
| `scanIntervalMs` 远大于 `stallThresholdMs`（如阈值 60s、周期 300s） | 卡死最多要 6 分钟才发现，阈值调了等于没调 |
| `cooldownMs: 0` + `scanIntervalMs: 5000` + `afterMs: 0` | 每 5 秒一次模型调用，一个卡住的回合能烧掉几十次 |
| `semanticReview.enabled: true` 但没配 `compressionModel` | 用主模型审查，成本按主模型算 |
| `enabled: false` 时以为「只关了心跳」 | L2 一起停——总开关管两层 |
| 改了 `stallThresholdMs` 没注意 `afterMs` 跟着变 | 语义审查的触发点被动漂移（缺省为阈值一半） |
| 给工具补了 `timeoutMs` 却没同步实际执行上限 | 声明小于实际 = 仍会被误杀；声明远大于实际 = 真卡死要等更久 |

## 七、边界（调参也改不掉的部分）

- **中断打不断正在执行的工具**。`ToolContext` 没有 signal，工具感知不到取消；看护中断后工具仍会跑到自己返回，`turn.end` 等到那时。看护保证的是「不再无限等」，不是「立即掐断」。兜底只能是工具自己的 `timeoutMs`——**有长跑可能的 6 个工具都已声明**：`bash`（30s）/ `run_command`（600s）/ `web_search`（10s）/ `dispatch_subagent`、`_batch`（前台 300s）/ `generate_image`（120s，provider 层 `timeout` 与工具声明共用同一常量、`maxRetries` 归零）；其余 9 个是本地快操作，不需要时限。
- **语义审查只看最近 6 步**（每步摘要截 240 字符，目标截 600 字符）。更长程的偏离它看不出来。
- **阈值是全局的**，不能按 agent 分别配置；同一台引擎上跑长任务和跑短对话只能用同一套参数。
- **审查结论不落盘**，只在日志里。想复盘判定依据需要自己留日志。
