## P0-1 config.json 原子写 + 损坏显式报错（cfde7cb）

**原问题**（数据 M7 / 体验 D-M6）：`ConfigRepository.save()` 裸 `fs.writeFile` 无 tmp+rename；`load()` 大 catch 吞掉所有错误回默认——文件损坏 → 静默回默认 → 用户任意一次保存把默认配置写回，加密 apiKey 永久丢失。同类裸写：write.ts、edit_file.ts、crypto.ts。

**修复方案**：save 改 tmp+rename（复用 `renameWithRetry`）；load 区分 ENOENT 与损坏，损坏时隔离为 `.corrupt-{ts}` 并显式抛错；同类裸写一并补齐。

**验证结果：真的修好。**

- 原子写落实：`config/repository.ts:141-145` tmp+rename，复用 EPERM/EBUSY/EACCES 重试机制（`memory/document-store.ts:24-39`）。write.ts:77-80、edit_file.ts:64-67、crypto.ts:23-35 均已同样改造；全仓 grep `writeFile` 无残留裸写（mind-files.ts:203 为 `flag:'wx'` 排他创建，语义安全）。master key 原子写确有必要——半截密钥文件可读但密钥错误，全部密文解密失败且不自愈。
- load 区分正确：ENOENT → 默认（:89-91）；其他读错误重抛（:92）；解析失败 → 隔离 + 显式抛错（:98-106）。REST 路径下错误文案可达客户端（Fastify v5 默认 handler 对 500 不掩码 message）。
- quarantine 覆盖陷阱已闭合：所有写路由均为 `load() → mutate → save()` 无 catch 兜底（routes/config.ts:24-31、compute.ts:88-203），load 抛错则 save 不会执行；隔离后 load 走 ENOENT → save 写新文件、不动隔离文件，密文 apiKey 留在隔离文件可人工恢复。
- 测试真实且实跑通过（8/8）：损坏场景断言隔离文件逐字节保留 + 后续 save 不动它；tmp+rename 有 rename spy 断言。

**新发现问题：**

- **Major-1：并发 save 共享固定 tmp 名，无写队列串行化。** `repository.ts:143` 固定 `config.json.tmp`，而隔壁 DocumentStore 恰恰为此建了按文件串行的 writeQueues（`document-store.ts:44-54`）却未复用。两个并发请求（如 PUT /config 与 POST /compute/providers 同时）交错时：A 写 tmp → B 覆盖 tmp → A rename 成功（内容是 B 的）→ B rename 撞 ENOENT 报 500。结果：B 报错、A 报 200 但 A 的修改静默丢失。
- **Major-2：decrypt 降级路径是原 bug 的同构残留。** `repository.ts:63-74` decryptValue 失败仅 warn、字段置 undefined，load 正常返回；随后任意一次 save（:131 `p.apiKey ? enc : undefined`）把所有 provider 的 apiKey 永久写成 undefined，`compute.ts:123` 的 `|| existing.apiKey` 合并救不了（existing 已是 undefined）。触发条件是 master key **暂时性**不可用（误设一次 `CLOUDMIND_MASTER_KEY` 等）——与本次修的"损坏 → 回默认 → save 覆盖"同一类数据丢失路径，只加了 warn 未阻断降级后的回写。
- Minor-3：WS chat 路径感知不到损坏报错（ws/handler.ts:78 对 getAgentWorker 无 try/catch），显式文案只进引擎日志。
- Minor-4：隔离失败时 `repository.ts:102` `.catch(() => {})` 吞错，但 :103-105 的报错文案仍声称"已隔离到 X"（行为安全，文案说谎）。
- Minor-5：合法 JSON 但结构非法（如 `"providers": null`）→ :115 裸 TypeError，不走隔离分支，无恢复指引。

## P0-3 engine 挂死恢复闭环（9a908f0 + 1bb50a6 + 25e6a26）

**原问题**（体验 D-B1/B2、D-M4）：supervisor 宽限期失败 return 永不监控、重启 5 次 break 永久放弃；前端 WS 断开无任何重连；engine 对 8848 被占无处理，直接 exit(1) 落入永久放弃路径。

**验证结果：主链路真的修好；引入一个 Major 回归，残留一个 Major 缺口。**

- EADDRINUSE 闭环：`bootstrap.ts:284-294` catch → `classifyListenError`（listen-error.ts:14-21，只认 `err.code==="EADDRINUSE"`）→ 中文提示含端口号 → exit 2；exit code 契约两侧一致（mod.rs:21 ↔ listen-error.ts:6）。supervisor 侧 `:188-198` exit 2 + /health 不通 → port_conflict 降级 30s 低频重试，无重启风暴；普通崩溃走 failures/backoff 路径，两种情形真的区分开了。
- supervisor 永不放弃属实：宽限失败不再 return（:155-161 记 error 后进主循环）；重启 5 次用尽不再 break（:210-218 转低频持续 restart）；主循环 `loop {}`（:166）内只有 continue，无静默退出路径；退避 2^n 有界（1/2/4/8/16s，:221），降级后固定 30s，无忙等、日志频率有界。
- 收编纳管：`:97-107` 收编注册进 SUPERVISOR（child=None），崩溃后走 restart spawn 新 child 转全纳管；测试验证不误杀外来进程。

**新发现问题：**

## P0-5 HNSW 增量索引 + search deadline 15s（afbc65d + b7cb6a4）

**原问题**（质量 B1，实测）：每次 upsert 置 dirty，search 前全量重建 HNSW（384 维：1k 条 3.97s 超 3s deadline、1 万条 123.8s），重建持写锁阻塞整个 tokio runtime；每轮对话 L4 检索都触发重建，超时后静默降级返回空，语义检索在千条规模即实质失效。

**修复方案**：upsert 直接 `index.insert` 单点增量插入（hnsw_rs `insert` 为 `&self`，官方支持并发）；search 改持读锁；≤256 条走精确线性扫描；重复 upsert 旧点成孤儿、search 只认 doc_ids 登记的最新点；冷载入并行化且挪出 INDEX_CACHE 写锁；启动时 compaction（tmp+rename）；search deadline 放宽至 15s。

**验证结果：核心修复真的落实，稳态 L4 失效问题已解；但两处 Major 使其只能算部分修好。**

- 增量插入属实：`vector/mod.rs:42-50` upsert 即插入，无 dirty 无重建路径；插入与 search 同一实例无快照层，upsert 后立即可搜（测试 vector_test.rs:148-163 真实覆盖）。重复 upsert：旧点孤儿化 + search `doc_ids`/`seen` 过滤（:64-79），不重复命中、不命中旧向量（测试 :167-183）。
- 并发改善属实但 commit 有夸大：search 持读锁（server.rs:47-50，diff 确认由 write 改来），upsert 持写锁。upsert 写锁**仍跨越 persist_append 的全部异步文件 IO**（mod.rs:49 → :103-129 三次 await），期间排除所有读者——量级从秒级降到毫秒级（测试 :187-219 证明 3000 次 upsert 期间 search max<500ms），但 commit 称"upsert/search 不再互阻塞"不准确。
- 线性阈值 256 合理：256×1536 维 ≈ 40 万乘加亚毫秒；两路径分数口径一致（线性 `1.0 - cosine` :92 ↔ DistCosine 同为 `1-cos` clamp≥0），边界无口径跳变。
- compaction 原子写落实：tmp+rename（:292-315）；只在 load_state 发布进 INDEX_CACHE 前执行（:185-187），无并发窗口；格式与旧版逐字节一致，老 embeddings.jsonl 正常加载。
- deadline：client.ts:128 search 15s 确认。
- 降级行为改善：超时仍返回空（indexer.ts:68-71），但 client.ts:92 有统一 warn，不再是"静默"。

**新发现问题：**

- **Major-1：HNSW 路径无维度校验，异维数据可致永久 panic。** 线性路径过滤异维向量（mod.rs:89），HNSW 路径（:66 `self.index.search`）与 upsert（:46 `insert`）都没有任何维度检查，而 anndists `DistCosine::eval` 第一行是 `assert_eq!(va.len(), vb.len())`。若 embeddings.jsonl 混入不同维度的历史数据（换 embedding provider 完全可能发生），一旦 ids>256，search 在距离求值处 panic；更糟的是冷载入 `parallel_insert`（:272-290）同样不校验——污染文件会让该 agent **每次冷载入都 panic，索引永久不可用，连重启都救不回来**。修法：upsert 入口校验维度与现有索引一致 + 载入时跳过异维行。
- **Major-2：15s deadline 的"余量"是无据断言，且 upsert 路径被遗漏。** 冷载入 3.8s 是万条 384 维实测；1536 维数据量 ×4（~176MB），解析与距离求值随维度线性放大，估算 **15-19s——15s 没有余量**。b7cb6a4 声称"含 1536 维生产嵌入的余量"但未给出任何 1536 维实测数据。且 upsert 仍是默认 3000ms（client.ts:79、:116 未覆盖，15_000 仅见 :128）——sidecar 重启后第一条写消息嵌入的 upsert 同样触发完整冷载入，万条级必然 DEADLINE_EXCEEDED，该条消息嵌入被丢弃。要么实测后放宽 deadline（search/upsert 一起），要么 sidecar 启动时预热 load。
- Minor：孤儿点永久驻留内存（compaction 只压盘不压索引），靠重启冷载入剔除，长期运行内存膨胀。
- Minor：冷载入窗口内同一 agent 的并发 search/upsert 各自完整重复构建（:156-159 注释承认）；`parallel_insert`/`parse_records_parallel` 用 `std::thread::scope` join 在 async worker 线程上同步阻塞，未走 spawn_blocking（:251-289）。
- Minor：compaction 无 fsync（与 :101 注释的取舍一致，嵌入是可重建冗余，可接受）；compaction 中序列化失败的 doc 被静默跳过即丢数据（:305 仅 warn）。
- Minor：`vector_test.rs:91-94` 的 "Reload from disk and verify persistence" 是假测试——INDEX_CACHE 是进程级静态，第二次 get_or_load 直接命中缓存返回同一 Arc，根本没读盘，断言恒真。
- commit 如实性：afbc65d 的增量插入/读锁化/孤儿去重/256 阈值/冷载入并行/compaction 均如实；"不再互阻塞"夸大（上）。b7cb6a4 的"1536 维余量"无据（上）。"cargo test 19 全绿"本次未运行构建，采信但标注。
