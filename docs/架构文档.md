## 1. 项目定位

CloudMind-Zome 是一个**单用户本地桌面应用**（也可作为 Web 应用运行），核心定位是"多 Agent 协作平台"。

- **单用户**：无登录/注册流程，所有数据本地存储
- **本地优先**：运行时数据落在 `~/.cloudmind-zome`（Windows 上为 `%USERPROFILE%\.cloudmind-zome`），可用环境变量 `CLOUDMIND_DATA_DIR` 覆盖
- **桌面封装**：Tauri 2（Rust + WebView2）。启动链：Tauri → Rust sidecar →（supervisor 守护）→ Node.js 引擎

### 1.1 核心功能（当前已实现）

## 2. 技术栈

| 层级 | 技术 |
|------|------|
| 后端框架 | Node.js 22 + Fastify 5 |
| 数据存储 | 文件系统（per-Agent JSON/JSONL，无数据库） |
| 向量检索 | Rust sidecar 自研 HNSW（instant-distance，余弦距离，append-only JSONL 增量持久化，dirty 标记惰性重建） |
| LLM 客户端 | OpenAI SDK（`openai`，兼容 OpenAI 协议的 Provider） |
| Token 计数 | engine 内 `@dqbd/tiktoken`（cl100k_base）；sidecar 另有 `tiktoken-rs`（按 model 缓存 CoreBPE 实例，单例懒加载） |
| 任务调度 | cron-parser + setInterval 轮询（`services/engine/src/scheduler/`） |
| 前端 | Nuxt 3 + Vue 3 + Pinia + TypeScript |
| 实时通信 | WebSocket（`@fastify/websocket`） |
| 桌面封装 | Tauri 2（Rust + WebView2） |
| 进程守护 | sidecar supervisor（健康检查复用静态 reqwest 客户端 + 指数退避重启，最多 5 次） |

## 4. 核心机制

### 4.1 AgentWorker — 单一数字生命

每个 Agent 对应全局唯一的 `AgentWorker`（`services/engine/src/core/agent-worker.ts`）：

- **一个内部队列** — FIFO 串行处理所有 Jobs
- **一个状态** — `idle` / `busy` / `paused`，由 Worker 单点维护
- **`runTurn()` 调用** — 每轮通过 `services/engine/src/core/react/turn.ts` 执行 ReAct 步骤
- **配置变更联动** — Agent 配置变更时 pause 并移除 Worker 缓存，下次懒重建

**Job 类型**：
- 正常对话 — 流式输出 text / thinking / tool_call
- 定时任务 — 由 Scheduler 触发，先持久化用户消息再入队
- Subagent 派发 — `runAgentCollect`，独立 `subagent_<uuid>` sessionId 收集完整输出

### 4.2 ReAct 循环

```
用户消息 → ContextPipeline.assemble 组装 → LLM 流式调用 → 解析响应
                                                        ↓
                                              ┌─────────┴─────────┐
                                              ↓                   ↓
                                        [普通回复]           [Tool Calls]
                                              ↓                   ↓
                                        保存并结束        执行工具 → 结果加入消息
                                                                    ↓
                                                            继续下一轮 LLM
```

- 单轮最多 **5 步**（maxSteps），超限截断
- **流式事件**（`LLMEvent`，`provider/types.ts`）：
  - `thinking.delta` — 推理内容（折叠显示）
  - `text.delta` — 正文内容
  - `tool.call` — 工具调用
  - `tool.result` — 工具执行结果
  - `step.end` — 单步结束（每个 ReAct step 都发，tool_use 时循环继续）
  - `turn.end` — 一轮结束（ReAct 循环退出后由 runTurn 发出；前端只在此时复位"生成中"状态）

### 4.3 ContextPipeline — L1–L6 分层组装（Phase 1–3 已完成）

`ContextPipeline`（`services/engine/src/context/pipeline.ts`）在每轮 LLM 调用前组装上下文（`core/react/turn.ts` 接入），预算默认 `maxContextTokens=80000`、`reserveRatio=0.1`（可按 Agent 配置，`core/pipeline-factory.ts`）。

| 层级 | 内容 | 降级策略 |
|------|------|----------|
| L1 | 人格系统提示（SOUL.md + Skill 注入；`src/mind/mind-files.ts`） | 不降级 |
| L2 | @提及提醒 | 不降级 |
| L3 | Hot Context（当前会话近期消息） | keep-15 → keep-10 → keep-5 截断 |
| L4 | 语义检索结果（`SemanticMemory[]`，score 降序） | keep-10 → 5 → 3 → 丢弃（保留高相关） |
| L5 | 话题摘要（最近压缩档，时间倒序） | drop-oldest 逐条丢弃最旧 |
| L6-core | 核心工具描述 | 不降级 |
| L6-ext | 扩展工具描述 | halve → 丢弃（当前无扩展工具） |

MIND.md 经验检索（`src/mind/mind-files.ts`，Phase 1 框架）不占独立层级：每轮按当前用户输入做规则版检索（关键词/bigram 匹配 `##` 分块，上限 3 块），命中时伪装成一条 assistant 历史消息注入 L3 之后；不参与降级与多轮去重。SOUL.md/MIND.md 位于 `agents/{agentId}/`，新建 Agent 时生成默认文件。

**降级顺序：L5 → L4 → L6-ext → L3**（`context/layers.ts` `DOWNGRADE_ORDER`）。

- Token 计数：`@dqbd/tiktoken` cl100k_base，每条消息 +4 overhead，与 provider 实际发送内容对齐（id/createdAt 不计入）
- 工具结果截断：单条上限 = 预算 × 20%（兜底 16000 tokens），保留头尾（`context/truncate.ts`）
- 截断时清理失去前置 assistant toolCalls 的孤儿 tool 消息，避免 provider 400
- L1.5（平台能力层）曾短暂存在，已于 2026-07-21 移除（commit `ba7f726`）

**L5 话题压缩（Phase 2，`src/memory/topic/`）**：

- **检测**（`detector.ts`，规则版）：显式切换词 / 时间间隔超窗（默认 30 分钟）/ 消息数达阈值（默认 20 条）→ 关闭当前话题；关键词/语义边界留待后续
- **压缩**（`compressor.ts`）：LLM 单程生成「话题主题 + 关键结论」，60s 超时，解析失败走原文兜底；压缩模型可用 `compressionModel` 指定（缺省主模型，失败不 fallback）
- **归档**：压缩档落盘 `_compressed/{topicId}.md`（frontmatter + Summary + Key Points + 原文 msg_ids）；原始消息先写入 `messages_archived.jsonl` 再从热存储移除（`IMessageRepository.archiveAndRemove`，可经 `getArchivedByIds` 恢复）；短话题（<4 条）不调 LLM 仅归档（`archiveOnly`）
- **注入**：每轮组装时取最近 `hotMemoryCount`（默认 2）个压缩档渲染进 L5
- **后台队列**（`queue.ts`）：串行 fire-and-forget；归档失败时隔离已写压缩档，避免"摘要+原文"重复注入
- **启动对账**（`memory/reconcile.ts`）：engine 启动时对每个 agent 对账"压缩档 msg_ids ∩ 热存储"，补归档"压缩档已写入但 archiveAndRemove 未完成"的孤儿消息（`ZOME_STARTUP_RECONCILE=false` 可关闭）；不覆盖"退出时仍在未关闭话题里"的消息（无压缩档指向，需重跑话题检测，未实现）

**L4 语义检索（Phase 3，`context/semantic.ts`）**：

- `SemanticRetriever`：候选放大 2 倍 → 当前历史去重 → 已压缩话题原文排除（读压缩档 msg_ids，不读归档全文）→ 相似度 × 分段时间衰减（<7d 1.0 / <30d 0.8 / <90d 0.5 / 保底 0.3）→ `semanticMinScore` 过滤 → `semanticTopK`（默认 10）
- sidecar 原始返回为**距离**（`1-cosine`），`MemoryIndexer.search` 出口统一换算为相似度
- 压缩档 msg_ids 汇总（`archivedMessageIds`）按档缓存，(mtimeMs, size) 指纹失效，L4 检索与启动对账复用，不再每轮全量读 `_compressed/*.md`
- 注入内容按 2000 字符截断（与索引侧一致）；跨场景命中渲染 `[来自: sessionId]` 标注

**Agent 级配置**（`packages/shared` `AgentConfig`，bootstrap 逐项透传）：`maxContextTokens`、`compressionModel`、`topicDetectionWindowMinutes`、`topicMessageThreshold`、`semanticSearchEnabled`（同时门控检索与索引）、`semanticTopK`、`semanticMinScore`。非法取值在引擎侧 clamp 并 warn。

### 4.4 记忆系统

```
┌─────────────────────────────────────────────┐
│  DocumentStore（memory/document-store.ts）   │
│  - 泛型 JSON/JSONL 文件存储                  │
│  - tmp+rename 原子写，按文件串行写队列        │
│  - Windows EPERM/EBUSY 递增退避重试 5 次     │
│  - readLines 读缓存（mtime+size 指纹失效，    │
│    进程内写主动失效，返回深拷贝防污染）        │
├─────────────────────────────────────────────┤
│  Repositories（memory/repositories/）        │
│  - agent.ts     → agents/<id>/agent.json     │
│  - message.ts   → agents/<id>/messages.jsonl │
│  - memory.ts    → agents/<id>/memories.jsonl │
│  - action.ts    → agents/<id>/actions.jsonl  │
│  - llm-call.ts  → agents/<id>/llm_calls.jsonl│
├─────────────────────────────────────────────┤
│  MemoryIndexer（memory/indexer.ts）          │
│  - embed：OpenAI SDK embedder（5s 超时包装） │

│  - sidecar 不可用时整体静默跳过              │
└─────────────────────────────────────────────┘
```

**跨会话语义检索**：已实现为 ContextPipeline 的 L4 层（`context/semantic.ts` 的 `SemanticRetriever`，见 §4.3）——embedder + sidecar HNSW 由 `MemoryIndexer` 承载，检索结果经 pipeline 注入、参与预算与降级；sidecar 不可用时静默降级为空。

### 4.5 工具系统

内置工具位于 `services/engine/src/tools/builtin/`，按 `agentConfig.tools` 名单启用：

| 工具 | 文件 | 审批 | 功能 |
|---|---|---|---|
| `read_file` | `builtin/read.ts` | 否 | 读取工作区/projectRoot 文件 |
| `write_file` | `builtin/write.ts` | 是 | 写入工作区 `files/` 子目录（code 模式为 projectRoot） |
| `edit_file` | `builtin/edit_file.ts` | 是 | oldString/newString 唯一匹配替换 |
| `list_files` | `builtin/list_files.ts` | 否 | 列目录（`recursive` 参数未实现） |
| `bash` | `builtin/bash.ts` | 是 | 白名单命令，禁 shell 元字符与脚本执行 |
| `run_command` | `builtin/run_command.ts` | 是（不可免问） | **无沙箱**任意 shell（code 模式），timeout 上限 600s |
| `dispatch_subagent` | `builtin/dispatch_subagent.ts` | 否 | 借用其他 Agent 执行子任务（前台/后台） |

**工具审批**：标记 `requiresApproval` 的工具（write_file / edit_file / bash / run_command）执行前需人工审批——交互式 WS 会话中前端弹出 inline 确认（`tool.approval_request` → `tool.approval`，60s 超时视为拒绝，可选"本会话不再询问"，**`run_command` 不参与免问**，`api/ws/validation.ts`）；无审批通道的调用方（定时任务、蓝图、subagent）一律拒绝。

**写入限制**：写入工具通过路径解析限制只能写入工作区 `files/` 子目录（code 模式为 projectRoot 内），并保护 `agent.json`、`messages.jsonl`、`config.json`、`.master-key` 等关键文件。

## 5. 通信架构

### 5.1 WebSocket 协议

两条路径（均无 `/api/v1` 前缀）：

- `GET /ws/:agentId?sessionId=xxx` — 私聊（`handler.ts`，sessionId 缺省 `"default"`）
- `GET /ws/sessions/:sessionId` — 群聊/会话（`session-handler.ts`）

**Client → Server**：
- `{ "text": "..." }` — 聊天消息（**无 type 字段**，最长 10000 字符）
- `tool.approval` — 审批回执（`approvalId` / `approved` / `remember`）
- `session.set_mode` — 切换 chat / code 模式（仅会话 WS，可带 `projectId`）
- 未知 type 帧静默忽略

**Server → Client**：
- `text.delta` / `thinking.delta` — 流式正文 / 推理
- `tool.call` / `tool.result` — 工具调用与执行结果
- `step.end` — ReAct 单步结束
- `tool.approval_request` — 审批请求（60s 未回视为拒绝）
- `session.mode_changed` — 模式切换确认
- `error` — 错误

握手校验 Origin（`api/ws/validation.ts`，防 CSWSH；无 Origin 的非浏览器客户端放行，Tauri 协议特判，`NODE_ENV=e2e` 全放行）。

### 5.2 群聊路由

```
用户消息
    │
    ▼
┌─────────────────────┐
│ Conductor           │
│ - @mention 精确路由  │（按成员 id 或 name 匹配）
│ - @all / @所有人     │ → 广播
│ - 无 @              │ → 广播给会话全部 Agent
└──────────┬──────────┘
           │
           ▼
    并行派发各 Agent Worker（各自串行回复）
```

> 旧架构的"语义意图路由 / 随机兜底"未迁入新架构，不存在。

### 5.3 心智互聊 (Intermind)

未实现。`Session.type` 仅保留 `"intermind"` 占位值（`conductor/types.ts`），无任何路由、编排或 WS 帧。

### 5.4 Agent 间私信

未实现。无 `send_private_message` 工具与私信链路。

## 6. 配置系统

### 6.1 引擎配置（`config.json`）

运行时从 `CLOUDMIND_DATA_DIR/config.json` 加载，由 `ConfigRepository`（`services/engine/src/config/repository.ts`）管理：

```json
{
  "providers": [],
  "settings": {
    "memory": {
      "compactThreshold": 0.8,
      "keepRecent": 3,
      "hotMemoryLimit": 10,
      "warmMemoryLimit": 20
    },
    "tavilyApiKey": "tvly-..."
  }
}
```

> 凭据（Provider API Key、`tavilyApiKey`）以 `enc:` 前缀经 `services/engine/src/config/crypto.ts` AES-256-GCM 加密后落盘；API 返回时脱敏为 `"***"`。

### 6.2 Provider 配置

Provider 配置统一存放在 `config.json` 的 `providers` 数组中，由算力平台界面（`apps/web/pages/compute.vue`）通过 REST API（`services/engine/src/api/routes/compute.ts`）读写。

- **前端入口**：`apps/web/pages/compute.vue`
- **后端路由**：`services/engine/src/api/routes/compute.ts`
- **配置仓库**：`services/engine/src/config/repository.ts`
- **凭据加密**：`services/engine/src/config/crypto.ts`（AES-256-GCM，主密钥来自 `CLOUDMIND_MASTER_KEY` 或自动生成的 `.master-key`）
- **SSRF 校验**：Provider `baseUrl` 禁止内网地址与文件协议（已知边角：`::ffff:` hex 形式与 DNS 重绑定可绕过，见 §9）
- **启动加载**：`services/engine/src/bootstrap.ts` 加载 `config.json` 并初始化 Provider

### 6.3 数据目录

```
DATA_DIR/  (~/.cloudmind-zome/)
├── config.json            # 全局配置（Provider、记忆参数）
├── .master-key            # 自动生成的 AES 主密钥（权限 0o600）
├── blueprints.jsonl       # 蓝图定义
├── skills/                # 全局 Skill 目录
└── agents/{agent_id}/     # Agent 工作区
    ├── agent.json         # Agent 元数据
    ├── messages.jsonl     # 会话消息（热存储）
    ├── messages_archived.jsonl  # 已归档消息（话题压缩后移入，可恢复）
    ├── _compressed/       # 话题压缩档（markdown + frontmatter）
    ├── memories.jsonl     # 长期记忆
    ├── actions.jsonl      # 动作记录
    ├── llm_calls.jsonl    # LLM 调用记录
    ├── scheduler.jsonl    # 定时任务
    ├── files/             # 工具可读写目录
    ├── skills/            # Agent 私有 Skill
    └── indices/hnsw/      # 向量索引（sidecar 写入）
```

> 注意：sidecar（Rust）使用独立的密钥约定——`ZOME_MASTER_KEY` 环境变量或 `{data_dir}/.master_key` 文件，与 engine 的 `CLOUDMIND_MASTER_KEY` / `.master-key` **不是同一套**。

## 7. 错误处理与恢复

### 7.1 现状

- **LLM 调用失败直接报错**：无错误分类、无指数退避、无 fallback 切换（`ProviderConfig.maxRetries` 字段存在但未消费）
- **sidecar 不可用**：向量索引/检索整体静默跳过，对话主流程不受影响
- **embed 超时**：5s `Promise.race` 包装，超时返回空结果
- **WS 脏帧**：非 string delta 帧丢弃并 warn；未知 type 帧静默忽略

### 7.2 SmartStop（现状）

- 单轮 ReAct 最多 5 步（maxSteps）硬截断
- ContextPipeline 预算降级（见 §4.3）防止超窗口
- 工具结果按预算 20% 截断，防止单条大结果击穿窗口
- 循环检测、token 上限熔断等完整 SmartStop 未实现

## 8. 安全模型

> CloudMind-Zome 是**单用户本地应用**，engine 绑定 `127.0.0.1`，HTTP/WS 无鉴权，以下针对本地桌面场景。

| 风险 | 现状 | 建议 |
|------|------|------|
| 单用户无隔离 | 无多用户支持，所有 Agent 共享同一用户上下文 | 如需多用户需整体扩展 |
| 文件系统逃逸 | `write_file` 限制在 `files/` 子目录；路径校验为纯词法比较，**symlink 可逃逸** projectRoot | 增加 realpath 校验或 chroot |
| 代码执行 | `run_command` 为**无沙箱**任意 shell（`bash` 工具是白名单）；写类工具全部接入人工审批，`run_command` 每次必问 | 蓝图/定时任务等非交互路径一律拒绝危险工具（已实现） |
| API Key 存储 | `config.json` 中 AES-256-GCM 加密（`services/engine/src/config/crypto.ts`） | 通过 `CLOUDMIND_MASTER_KEY` 覆盖主密钥 |
| SSRF 防护 | Provider `baseUrl` 已校验，但可被 `[::ffff:7f00:1]` 等 hex 形式绕过，且不防 DNS 重绑定 | 完善 IP 段覆盖与 DNS 解析校验 |
| WS 鉴权 | 握手已校验 Origin（`services/engine/src/api/ws/validation.ts`），无 token 鉴权 | 生产环境增加 token 验证 |

## 9. 已知限制

| 限制 | 现状 | 影响 |
|------|------|------|
| Plan / Subagent 后台任务内存态 | `PlanManager` 与 `BackgroundManager` 均为内存 Map | 重启即丢 |
| 消息全量加载 | 无分页，历史全量读入 | 长期对话可能卡顿 |
| sidecar 可选 | 不可用时向量记忆静默降级 | 无语义检索但对话正常 |
| HNSW 索引 | 内存索引 + append-only JSONL 增量持久化（upsert 置 dirty，search 时惰性重建一次） | 大数据量性能未验证 |
| 无 LLM 重试/降级 | 调用失败直接报错 | Provider 抖动直接表现为对话失败 |
| run_command 无沙箱 | 依赖人工审批兜底 | 审批误放行即任意执行 |
