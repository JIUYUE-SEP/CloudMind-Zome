## 1. 项目定位

CloudMind-Zome 是一个**单用户本地 Web 应用**（engine + Nuxt 前端），核心定位是"多 Agent 协作平台"。

- **单用户**：无登录/注册流程，所有数据本地存储
- **本地优先**：运行时数据默认落在 `~/.cloudmind-zome`（sidecar 若运行会解析统一数据目录并在其启动 engine 时注入；旧默认目录数据由 sidecar 启动时一次性迁移）。均可用 `CLOUDMIND_DATA_DIR` 覆盖（详见 §6.3）
- **形态**：Web 应用（engine + web 前端）；Rust sidecar 为可选性能组件（向量记忆），不启动则语义检索静默降级

### 3.2 层间边界

**前端（`apps/web/`）→ 引擎（`services/engine/`）**：通过 REST / WebSocket 直连（无代理，engine 绑定 `127.0.0.1:8848`）
**引擎（`services/engine/`）→ Rust sidecar（`crates/zome-sidecar/`）**：通过 gRPC（默认 `127.0.0.1:50051`）调用；sidecar **可选**，不可用时向量记忆静默降级，其余功能不受影响。启动路径两条：手动 `cargo run`（engine 纳用不重复拉起），或自启唤醒（`settings.sidecarAutoStart` 默认关——engine listen 后 fire-and-forget 拉起，五档二进制发现序，全灭 warn 降级不炸启动；engine 关停两段式终止子进程；其 supervisor 收编拓扑既有——sidecar 启动见 engine.pid 纳管不重复 spawn）

## 4. 核心机制

### 4.1 AgentWorker — 单一数字生命

每个 Agent 对应全局唯一的 `AgentWorker`（`services/engine/src/core/agent-worker.ts`）：

- **一个内部队列** — FIFO 串行处理所有 Jobs
- **一个状态** — `idle` / `busy` / `paused`，由 Worker 单点维护
- **`runTurn()` 调用** — 每轮通过 `services/engine/src/core/react/turn.ts` 执行 ReAct 步骤
- **配置变更联动** — worker 生命周期由 `WorkerRegistry`（`core/worker-registry.ts`，P3-6）单点权威：配置变更经 `retire()` 退役旧 worker（排队 job 显式 settle、在途 turn 排空后才替换，FIFO 串行不变量不破），下次 `getOrCreate` 按新配置懒重建

**Job 类型**：
- 正常对话 — 流式输出 text / thinking / tool_call
- 定时任务 — 由 Scheduler 触发，先持久化用户消息再入队
- Subagent 派发 — `runAgentCollect`，独立 `subagent_<uuid>` sessionId 收集完整输出
- 系统通知 — Subagent 终态经 `enqueueSystemNotice` 注入的 `[系统通知]` 感知回合（通用注入通道；产出写历史；开关 `subagentNotify` 缺省开；notified 幂等）——Intermind inbox 地基
- 瞬态回合 — 蓝图等非人形工作流置 `ephemeral` 标记（`core/agent-worker.ts` Job.ephemeral）：本轮不落 agent 热存储、不进话题 tracker/压缩/向量索引、不触发话题裁判（`core/agent-worker.ts` onStepAppended 与 turn 收尾分支、`blueprint/engine.ts`），会话历史与人格记忆零污染；LLM 调用记录（`llm_calls.jsonl`）由 provider 包装层负责，不受该标记影响

### 4.2 ReAct 循环

```
用户消息 → ContextPipeline.assemble 组装 → LLM 流式调用 → 解析响应
                                                        ↓
                                              ┌─────────┴─────────┐
                                              ↓                   ↓
                                        [普通回复]           [Tool Calls]
                                              ↓                   ↓
                                        保存并结束        执行工具 → 结果加入消息
                                                                    ↓
                                                            继续下一轮 LLM
```

- 单轮以**上下文水位**为主判据（70% 提醒、90% 撞顶兜底）；`reactMaxSteps` 退化为防空转保险丝（缺省 100，agent 可配，clamp 1-500）；撞顶后追加一次无工具总结调用强制产出最终回复，兜底也失败则回复「我查了很多资料但没能整理好答案，请再问我一次」——回合永远有 assistant 回复，绝不静默
- **首步预检（G1）**：循环开始前先算一次水位——≥90% 不进循环直接走水位兜底、70%-90% 先注入 system 提醒再进循环（与循环内检查共享"每回合至多一次"语义）；预检前先调 `provider.refresh()`，型号表 PUT 改 apiMode 后本轮预检即新口径（`core/react/turn.ts`）
- **水位口径（H3/F1）**：U = max(实测, 估算)——实测 = provider `step.end` 透传 usage（权威回报；`promptTokens`/`completionTokens` 分别过 `Number.isFinite`，任一 NaN 即弃用该路，防 NaN 静默改判水位）；估算 = 本地 token 计数（当前 messages 含刚追加的工具结果 + 工具定义，与 pipeline 预算同口径），缺哪路用哪路。估算默认剥 thinking：chat_completions 请求回传不含 think 块；Anthropic/Responses 真回传 thinking，由实测口径兜底计入（取大不低估）。首步预检无实测可用，调用方按 `provider.protocol` 显式传入是否剥 thinking（`core/react/turn.ts` contextUsedTokens）
- **降级协议口径（S2/F1）**：`ResilientLLMProvider.protocol` 跟随当前活跃 provider——降级到不同协议的备用后预检口径跟着换；每次 chat 调用开始与 finally 双复位回主 provider，新回合预检读到的仍是主协议（`provider/resilient.ts`）
- **不变量（R2）**：`protocol()` 是单值口径（绑定 Router.defaultModel 生效协议），runTurn 必须以 provider.defaultModel 发起；传入其他型号时 warn 一次留痕、不 crash（`core/react/turn.ts` + `provider/protocols/index.ts`）
- **撞顶 = 换班移交**：水位撞顶不静默死亡，产出交接书并走自动续跑（见 §4.3）
- **流式事件**（`LLMEvent`，`provider/types.ts`）：
  - `thinking.delta` — 推理内容（折叠显示）
  - `text.delta` — 正文内容
  - `tool.call` — 工具调用
  - `tool.result` — 工具执行结果
  - `step.end` — 单步结束（每个 ReAct step 都发，tool_use 时循环继续）
  - `turn.end` — 一轮结束（ReAct 循环退出后由 runTurn 发出；前端只在此时复位"生成中"状态）

### 4.3 换班移交（交接书四件套 + 仲裁面）

**水位撞顶 = 换班移交（换班不死）**：撞顶兜底不静默死亡——runTurn 产出交接书消息载体，续跑循环自动换棒；连续撞顶由棒数保险丝封顶。

**交接书四件套**：

1. **三分法写作指引（件1）**：撞顶兜底后按【任务目的】【已完成】【未来方向】三节写交接书——任务目的用用户原话锚定（防目标漂移）、已完成每项一句话+指针 id 且把上一棒已完成滚动并入（防重复劳动）、未来方向给下一步具体动作/id（防重新规划）；体积约束写进指引（每项一句话、发现清单超长自行合并）（`core/react/turn.ts` HANDOFF_WRITING_GUIDANCE）
2. **足迹机械附（件2）**：引擎扫本回合 assistant 消息的 `toolCalls` 生成打卡清单（`name(参数JSON)`，单条 80 字符 / 总长 500 字符截断，无工具调用省略）——事实层由引擎机械生成，模型只写意义层（三分法正文），不靠模型回忆打卡（`core/react/turn.ts` formatFootprintItem / formatHandoffFootprint）
3. **瘦身写作间（件3）**：交接书正文改**独立小调用**（单步、无工具、no-op emit 不向用户流式转发），材料包四样 = 任务原消息（截 2000；优先 `repository.firstUserMessageBySession` 跨热存储+归档按 createdAt 时间序扫描，不受续跑最近 20 条窗口限制，查不到退回窗口内首条用户消息）+ 上一棒交接书（优先控制面 `handoff.bookText`，窗口扫描仅兜底；截 3000 且保尾切头标注，【未来方向】存活）+ 本棒足迹 + 本棒回顾（截 2000）；产出截 3000；失败/空文本/违规工具调用降级为兜底总结文本装入（`core/react/turn.ts` writeHandoffBookContent）
4. **开工指引（件4）**：续跑 job 由 pipeline `handoffPinned` 置顶注入固定指引 + 交接书原文——「从【未来方向】直接继续执行，不要重复已完成步骤/重新汇报已知进展；需要历史细节用 recall 按指针取回，不要凭印象编造」，固定层注入、不参与降级（`core/agent-worker.ts` HANDOFF_RESUME_GUIDE / contextPipeline input.handoffPinned）

**消息载体与事件**：交接书是 `[交接书]` 前缀 system 消息（内容 = 三分法正文或降级兜底；元信息 = 已用/窗口与百分比、棒次 `shift/maxShifts`、足迹行），随 `onStepAppended` 落历史可回溯（`core/react/turn.ts` makeHandoffBook）；撞顶后 AgentWorker 补发 `handoff.book` 事件（shift/maxShifts/used/window/bookMessageId/bookText/chainId），ws 层续跑循环据此写控制面（`core/agent-worker.ts`、`provider/types.ts` HandoffBookEvent）。

**仲裁面（loop 每连接一份 vs record 全局单条目）**：

- 控制面 `handoff-state.json`（DocumentStore 原子写 + schemaVersion 戳；损坏隔离 `.corrupt-<ts>-<随机后缀>` 空态启动，不覆盖坏数据）：同一 agent+session 只有一条活跃 record（稳定 id `ho_<agent>_<session>`，换棒覆盖不堆积）；状态机 pending→scheduled→running→completed/fused/aborted/lost，终态不可再转移，`record()` 重建 pending 是"新链"语义（`handoff/types.ts`、`handoff/state.ts`、`handoff/manager.ts`）
- **不对称起源**：续跑 loop 是每 WS 连接一个（各自持定时器与 AbortController），manager 是全局单例；`HandoffLoopRegistry` 是两者之间的唯一桥——cancel 统一走 registry 的 **agent+session 维度仲裁入口**（用户消息 / REST DELETE / 断连共用），一次完成"全局 record 取消 + 该维度下所有连接的 loop 打断（清定时器 + abort 在途 job）"，不存在只扫本连接的路径（`handoff/registry.ts`、`api/ws/handler.ts`）
- **断连专用 cancelConnection（V3 半开重连）**：注销本连接 loop；维度内仍有其他活跃链持有者时只取消本连接资源、不触碰全局 record（旧连接迟到 close 不杀新连接活跃链）；无其他连接/本连接是唯一持有者才落全局 aborted（`handoff/registry.ts` cancelConnection）
- **chainId 随 record 持久化**：首棒入控制面时由 `beginNewChain` 签发代际，续跑棒继承并落盘（重启后闩锁/对账仍可追溯旧链）；`beginNewChain` **只在打断了在途活跃链时轮换**——无活跃链沿用当前代际（连发两条消息、第一条撞顶产 book 时不误杀）；abort/断连清空本地代际（`handoff/types.ts` chainId、`handoff/resume-loop.ts` beginNewChain/cancel）
- **闩锁锚点 = record.chainId（P2-1）**：`handleBook` 入口对活跃 record 比对持久化 chainId，只有同链 book 才能覆盖/续跑——双 tab 竞态下 B 的 book 不顶替 A 的 record；aborted/lost 后旧链迟到 book 仅在代际匹配当前链时放行；`startResume` 入队前再与最新 record.chainId 复核，不一致不调度（`handoff/resume-loop.ts` handleBook/startResume）
- **onJobDone 代际复核 + 防御**：job 快照与控制面条目双重代际比对，控制面不存在/状态非 running/本 job 已产 book（booked，链由下一环接管）时跳过收尾；状态转移异常 try/catch 记档不浮空；`resume_history_failed` 等失败收尾同样走 registry 仲裁面（`handoff/resume-loop.ts` onJobDone、`api/ws/handler.ts`）
- **启动对账**：活跃条目（pending/scheduled/running）一律标 lost + `abortReason=engine_restart`，重启后不再自动续跑（同 subagent lost 语义，现场已毁交人工决策）（`handoff/state.ts` markActiveAsLost）
- **保险丝**：`shift >= maxShifts` → fused 停止自动续跑；缺省 5 棒，clamp 1-10，agent 可配 `handoffMaxShifts`（`handoff/types.ts`、`handoff/resume-loop.ts` handleBook）
- **群聊暂不自动续跑**（交接书照常落历史）：续跑循环只在私聊连接上建立（`api/ws/handler.ts`）

**Phase 4（2026-08-19 完成）**：

- **memory flush（设计决策 6 落地）**：压缩调用新增「长期记忆」产出区——值得跨话题记住的事实/决策/情感表达（一句话一条 + 置信度，≤0.5 不落盘、上限 5 条/话题，防注入声明覆盖），归档成功后落 `memories.jsonl`（其首个生产写入方）+ embed 入向量索引（doc_id `mem:<recordId>`，L4 可召回）；写入前文本精确去重（防队列重试/重复压缩重复落盘）。MIND=经验（我学到什么）与 memories=事实（发生了什么）分工
- **importance 真实赋值 + 差异化保留**：importance 由压缩调用评（high/normal/low，落压缩档 frontmatter）；L5 在最近 hotMemoryCount 个之外追加最近一个 high 档常驻注入（不被新话题挤出；追加档置末尾，drop-oldest 口径不破）；L4 的 mem: flush 条目继承话题 importance，high 恒不衰减（兑现决策 5 的未实现承诺）
- **双程压缩（Agent 级 `twoPassCompression`，缺省关）**：草稿→修订两程（同模型各带超时），第二程失败/空输出回退草稿（永不更差），缺省关的 agent 行为逐字节不变
- **用户可审计接口**：`GET /agents/:id/topics`（列表）/ `GET .../topics/:topicId`（全文）/ `POST .../restore`（恢复即删档：原文写回热存储 + 删档 + reindex；归档缺行计数 missing；重复 404 幂等）——归并读同 id 去重（热存储副本为幸存权威）
- 存量压缩档 importance=normal 无需迁移；对账补压缩路径不接 flush/twoPass（维持现状，永不更差）

**降级顺序：L5 → L4 → L6-ext → L3**（`context/layers.ts` `DOWNGRADE_ORDER`）。

- Token 计数：`@dqbd/tiktoken` cl100k_base，每条消息 +4 overhead，与 provider 实际发送内容对齐（id/createdAt 不计入）
- 工具结果截断：单条上限 = 预算 × 20%（兜底 16000 tokens），保留头尾（`context/truncate.ts`）
- 截断时清理失去前置 assistant toolCalls 的孤儿 tool 消息，避免 provider 400
- L1.5（平台能力层）曾短暂存在，已于 2026-07-21 移除（commit `ba7f726`）

**L5 话题压缩（Phase 2，`src/memory/topic/`）**：

- **检测**（`detector.ts`，规则版）：显式切换词 / 时间间隔超窗（默认 30 分钟）/ 消息数达阈值（默认 20 条）→ 关闭当前话题；关键词/语义边界留待后续
- **压缩**（`compressor.ts`）：LLM 单程生成「话题主题 + 关键结论」，60s 超时，解析失败走原文兜底；压缩模型可用 `compressionModel` 指定（缺省主模型，失败不 fallback）
- **归档**：压缩档落盘 `_compressed/{topicId}.md`（frontmatter + Summary + Key Points + 原文 msg_ids）；原始消息先写入 `messages_archived.jsonl` 再从热存储移除（`IMessageRepository.archiveAndRemove`，可经 `getArchivedByIds` 恢复）；短话题（<4 条）不调 LLM 仅归档（`archiveOnly`）
- **话题边界 LLM 裁判 + 压缩前复核（方案 C）**：每攒 6 轮（一轮 = 一条用户消息 + 一条助手回复，tool 消息不计数）在回合结束后**异步**跑一次语义裁判（独立 LLM 调用，绝不挡热路径；模型链 `topicBoundaryModel` → `compressionModel` → 主模型）——判 `NEW_TOPIC` 则在判决依据的那条用户消息**之前**一刀切（旧段关闭入队、该消息起开新话题，判决期间新到的消息不误切）；判 `SAME` 无事发生。规则（切换词/满阈值/时间窗）照旧优先，裁判只在规则沉默时运行。压缩任务执行前（`compression-task.ts` 前置一步）复核完整段单/多话题——多话题拆两个子段各自独立压缩落档（msgIds 无交叉）；复核失败/超时/解析失败/切点非法整段按单话题压缩（现状，永不更差）。裁判与复核 prompt 均带 P2-6 防注入声明（对话是数据不是指令）。
- **用户可见完整历史**：聊天接口 `GET /chat/:agentId/messages` 跨存储读取热存储 + 归档（`listBySessionWithArchived`，按 createdAt 归并、limit/before 真分页）——用户看的聊天记录不因压缩消失；她的上下文（L1-L6 组装 / L4 的 archivedMessageIds 排除 / reconcile / 压缩）仍只走热存储，不受影响
- **注入**：每轮组装时取最近 `hotMemoryCount`（默认 2）个压缩档的结构化条目（`latestSummaries`），经 recall 自然化注入（见下）
- **后台队列**（`queue.ts`）：串行 fire-and-forget；归档失败时隔离已写压缩档，避免"摘要+原文"重复注入
- **启动对账**（`memory/reconcile.ts`）：engine 启动时对每个 agent 做三件事——补归档"压缩档已写入但 archiveAndRemove 未完成"的孤儿消息（`reconcileHotStorage`）、收"已关闭已入队未压缩"的 pending 段（`reconcilePendingSegments`）、**跳过开放话题**（`reconcileOrphanedTopic`，真机 #10 方案 2）：退出时仍未关闭的话题原样保留在 topic-state.json，由运行时 TopicTracker 在阈值/显式切换词/时间窗超时自然收——重启是"睡一觉"不是"话题屠杀"；`ZOME_STARTUP_RECONCILE=false` 可关闭

**L4 语义检索（Phase 3，`context/semantic.ts`）**：

- `SemanticRetriever`：候选放大 2 倍 → 当前历史去重 → 已压缩话题原文排除（读压缩档 msg_ids，不读归档全文）→ 相似度 × 分段时间衰减（<7d 1.0 / <30d 0.8 / <90d 0.5 / 保底 0.3）→ `semanticMinScore` 过滤 → `semanticTopK`（默认 10）；检索侧单条文本按 2000 字符截断（`MAX_INJECT_CHARS`，与索引侧一致）
- sidecar 原始返回为**距离**（`1-cosine`），`MemoryIndexer.search` 出口统一换算为相似度
- 压缩档 msg_ids 汇总（`archivedMessageIds`）按档缓存，(mtimeMs, size) 指纹失效，L4 检索与启动对账复用，不再每轮全量读 `_compressed/*.md`

**L4/L5 注入（Phase 5 记忆自然化，`context/recall.ts` + `assembler.ts`）**：

- 不以 system 元信息注入，而是改写为第三人称、带原始时间戳的**伪装 user 历史消息**，与 L3 真实历史按 createdAt 归并穿插（`assembler.ts`）；L1/L2 保持相邻固定前缀（缓存友好）
- 置信度三档（`classifyScore`）：score > 0.7 正常注入；(0.5, 0.7] 模糊化（"好像提到过…这段记忆有些模糊"）；≤ 0.5 丢弃——pipeline 层的 `CONFIDENCE_DROP` 过滤是 `semanticMinScore` 之外的额外门槛
- 单条注入上限 **500 字符**（`MAX_MEMORY_CHARS`，超出摘要化：保留首尾、标注中段省略字数）；2000 字符上限只在检索/索引侧，不是注入上限
- 跨场景命中自然化标注"在另一个对话里"（旧的 `[来自: sessionId]` 标注已移除）
- 时间真实：正文渲染 `[YYYY-MM-DD HH:mm · N天前]`，伪装消息 createdAt 保留原始时间戳
- 多轮去重：同会话（sourceId）已注入条目 id 记录跳过（64 会话 FIFO）；检索失败不伪装，尾随 system 消息明确告知（`retrievalFailedMessage`）
- 规程自动恢复（skillRestore 通道，阶段 5 二期）：最近一条 L5 摘要 frontmatter 记 `usedSkills` 时，组装经 skillService 重取这些技能正文，以尾部独立 system 消息注入（不碰 L1 固定前缀；声明「规程数据、安全准则优先」；单技能截 4000 / 总量截 8000；取失败静默跳过；保护期 = 该摘要为最新 L5 的窗口）

**Agent 级配置**（`packages/shared` `AgentConfig`，bootstrap 逐项透传）：`maxContextTokens`、`reactMaxSteps`（ReAct 防空转保险丝，缺省 100，clamp 1-500）、`compressionModel`、`topicBoundaryModel`（话题边界裁判/复核模型）、`topicDetectionWindowMinutes`、`topicMessageThreshold`、`semanticSearchEnabled`（同时门控检索与索引）、`semanticTopK`、`semanticMinScore`。非法取值在引擎侧 clamp 并 warn。

| `recall` | `builtin/recall.ts` | 否（只读） | 回忆工具（上阁楼）：topics 浏览压缩档目录（label/起止时间/msgCount，时间倒序分页）+ read 按 topicId/关键词取归档原文（带时间戳，分页 + 翻页指引）；单条/总输出截断护栏；免审批、需白名单授权；傀儡硬禁（傀儡无记忆）；L4 排除语义不受影响 |

**工具审批**：标记 `requiresApproval` 的工具（write_file / edit_file / bash / run_command / dispatch_subagent / dispatch_subagent_batch / web_search）执行前需人工审批——交互式 WS 会话中前端弹出 inline 确认（`tool.approval_request` → `tool.approval`，60s 超时视为拒绝，可选"本会话不再询问"）；其中 `run_command` / `write_file` / `edit_file` / `dispatch_subagent` / `dispatch_subagent_batch` 不参与免问（`NO_REMEMBER_TOOLS`，`packages/shared/src/constants.ts`）——裸 shell、写操作与跨 agent 派发"remember 一次 = 放行一切"，一律每次批；`web_search` 不在不可免问名单，可「本会话免问」；无审批通道的调用方（定时任务、蓝图、subagent）一律拒绝。`send_private_message` 是社交动作：免审批、需白名单显式授权、每次写信写 warn 级审计（谁给谁写了什么，内容摘要截 200）。

**全部信任开关（`AgentConfig.trustAllTools`）**：agent 级开关，缺省 `false`（安全默认）。开启后该 agent 的需审批工具在**有审批通道**时自动批准（含不可免问五工具——用户明确信任即放行，这正是开关的意义），不再询问前端；每次自动放行写审计事件 `trusted-auto-approve`（工具名 + 参数摘要，沿用既有脱敏）——用户主权最终体现，审计留痕。无审批通道的路径（定时任务、蓝图、无桥接 subagent/后台傀儡）不受开关影响，仍 fail-closed 拒绝，防止静默越权。

**Puppet 型号库**（`subagent/puppet-models.ts`）：型号 = 命名预设包（`{ name, description, personaSnippet, suggestedTools? }`）。内置四型号（规划师/码农/调研员/审查员，代码常量）；自定义走 `DATA_DIR/puppet-models/*.json`（每型号一文件，zod 字段校验，坏文件跳过 warn，缺失目录按空），同名自定义覆盖内置并 warn（用户主权）。`dispatch_subagent` 的 `kind=puppet` 可选 `puppetModel`：persona 片段拼入傀儡基础设定（不改变傀儡制语义——仍无 SOUL/无 MIND）；`suggestedTools` 有值时傀儡最终工具 = 调用方 agent 白名单 ∩ 型号推荐（只窄化绝不扩权，交集为空拒绝派遣并明确报错）；型号不存在返回明确错误并列出可用型号。只读端点 `GET /puppet-models`（每项带 `source: builtin/custom`），第一版无 CRUD 写端点。

**写入限制**：写入工具通过路径解析限制只能写入工作区 `files/` 子目录，并保护 `agent.json`、`messages.jsonl`、`config.json`、`.master-key` 等关键文件。

**MCP 工具**（`tools/mcp/`）：`DATA_DIR/mcp-servers.json` 配置 stdio server，engine 启动连接（单 server 失败降级不阻塞整体）；每个 MCP tool 包装为 `mcp__<server>__<tool>` 命名工具（白名单字符 + 下划线折叠，64 字符封顶 FNV-1a 哈希后缀；同名冲突跳过记 warn），与内置工具同管线注入。审批 fail-closed：仅 `readOnlyHint===true` 免审批；`toolOverrides` 按限定名覆盖（显式免审批 / 强制审批 / `allowRemember` 放行——`mcp__` 前缀默认禁「本会话免问」）。调用失败自愈封顶一次（ping 探活分流 + single-flight 重连后重试，at-least-once 取舍）；server 断线工具保注册（调用时重连）。Windows 经 shim 启动并清理进程树。

## 5. 通信架构

### 5.1 WebSocket 协议

两条路径（均无 `/api/v1` 前缀）：

- `GET /ws/:agentId?sessionId=xxx` — 私聊（`handler.ts`，sessionId 缺省 `"default"`）
- `GET /ws/sessions/:sessionId` — 群聊/会话（`session-handler.ts`）

**Client → Server**：
- `{ "text": "..." }` — 聊天消息（**无 type 字段**，最长 10000 字符）
- `tool.approval` — 审批回执（`approvalId` / `approved` / `remember`；remember 对 `NO_REMEMBER_TOOLS` 五工具无效，见 §4.6）
- 未知 type 帧静默忽略

**Server → Client**：
- `text.delta` / `thinking.delta` — 流式正文 / 推理
- `tool.call` / `tool.result` — 工具调用与执行结果
- `step.end` — ReAct 单步结束
- `tool.approval_request` — 审批请求（60s 未回视为拒绝）
- `error` — 错误

握手校验 Origin（`api/ws/validation.ts`，防 CSWSH；无 Origin 的非浏览器客户端放行，`NODE_ENV=e2e` 全放行）。

### 5.2 群聊路由

```
用户消息
    │
    ▼
┌─────────────────────┐
│ Conductor           │
│ - @mention 精确路由  │（按成员 id 或 name 匹配）
│ - @all / @所有人     │ → 广播
│ - 无 @              │ → 广播给会话全部 Agent
└──────────┬──────────┘
           │
           ▼
    并行派发各 Agent Worker（各自串行回复）
```

> 旧架构的"语义意图路由 / 随机兜底"未迁入新架构，不存在。

### 5.3 心智互聊 (Intermind)

已实现一期（人形间私信）：`send_private_message` 工具写信——邮箱对称双写（接收方 `intermind:<fromAgentId>` 来信线程 + 发送方 `intermind:<toAgentId>` 来往线程留底），信到后经 `enqueueSystemNotice` 触发接收方一轮感知回合（通知文本「【来自 {name} 的私信】{摘要}」，sourceId 独立 notice 会话）；感知回合带 `intermindRide` 标记，回信只入队不再次唤醒（搭车）。通知摘要截断（200 字）时追加读全文指引，接收方可用 `read_private_messages`（`from: {senderId}`）从自己信箱取完整来往信件（免审批、需白名单授权、傀儡硬禁）。防连环唤醒三防线：搭车标记 + 感知回合无审批通道（写类/派发 fail-closed，无法在感知回合内再派分身）+ 傀儡上下文硬拒。REST 只读：`GET /agents/:id/intermind`、`GET /agents/:id/intermind/:peerId/messages`。容量治理（2026-08-17，H8）：intermind 会话不参与话题压缩，热存储按条数封顶（`INTERMIND_HOT_LIMIT=200`），写信后溢出部分经 `archiveAndRemove` 先归档后删热存储（`messages_archived.jsonl`，可恢复），归档失败仅 warn 不炸写信；读取走 `listBySessionWithArchived` 跨存储归并（before 游标校验同跨热存储+归档），归档后历史完整可读。设计文档：`docs/design/intermind.md`。待办：免打扰开关、前端 UI、`sessions.jsonl` 显式会话记录。

#### 型号级 apiMode 覆盖（2026-08-10 B 方案）

- `ModelInfo.apiMode`（三族值，可选）：型号级协议覆盖，**缺省 = 沿用 `ProviderConfig.apiMode`**；仅当型号表存在至少一个 apiMode 覆盖时 bootstrap 才走 `ModelApiModeRouter`，无覆盖保持既有 per-provider 单实例路径、行为完全不变（`provider/protocols/index.ts` hasModelApiModeOverride、`bootstrap.ts` createLLMProvider）

## 7. 错误处理与恢复

### 7.1 现状

- **LLM 调用韧性层**：错误分类重试（429/5xx/网络/超时指数退避，流式调用仅首事件前重试保安全）+ Agent 级 `fallbackProviderIds` 降级链 + `requestTimeout`/`maxRetries` 消费（`provider/resilient*.ts`）
- **sidecar 不可用**：向量索引/检索整体静默跳过，对话主流程不受影响
- **embed 超时**：5s `Promise.race` 包装，超时返回空结果
- **WS 脏帧**：非 string delta 帧丢弃并 warn；未知 type 帧静默忽略

### 7.2 SmartStop（现状）

- 单轮 ReAct 以上下文水位为主判据（70% 提醒 / 90% 撞顶兜底）；`reactMaxSteps` 退化为防空转保险丝（缺省 100，clamp 1-500）；撞顶强制无工具总结兜底（不静默）
- ContextPipeline 预算降级（见 §4.4）防止超窗口
- 工具结果按预算 20% 截断，防止单条大结果击穿窗口
- 循环检测、token 上限熔断等完整 SmartStop 未实现

## 8. 安全模型

> CloudMind-Zome 是**单用户本地应用**，engine 绑定 `127.0.0.1`；REST 全局 Bearer 鉴权（P0-2：除 `/health`、`/ws/*` 外全部端点含 `/docs` 要求 `Authorization: Bearer <token>`——32 字节随机 token 落盘 `DATA_DIR/auth-token`（0600），`CLOUDMIND_AUTH_TOKEN` 可覆盖，常量时间比较），WS 握手 token 走 `Sec-WebSocket-Protocol` + Origin 白名单（防 CSWSH，违规 4401/4403）。以下针对本地单用户场景。

| 风险 | 现状 | 建议 |
|------|------|------|
| 单用户无隔离 | 无多用户支持，所有 Agent 共享同一用户上下文 | 如需多用户需整体扩展 |
| 文件系统逃逸 | `write_file` 限制在 `files/` 子目录；路径校验为纯词法比较，**symlink 可逃逸** projectRoot | 增加 realpath 校验或 chroot |
| 代码执行 | `run_command` 为**无沙箱**任意 shell（`bash` 工具是白名单）；写类工具与 dispatch_subagent 全部接入人工审批，`run_command`/`write_file`/`edit_file`/`dispatch_subagent` 每次必问（不可免问） | 蓝图/定时任务等非交互路径一律拒绝危险工具（已实现） |
| API Key 存储 | `config.json` 中 AES-256-GCM 加密（`services/engine/src/config/crypto.ts`） | 通过 `CLOUDMIND_MASTER_KEY` 覆盖主密钥 |
| SSRF 防护 | Provider `baseUrl` 已校验：协议白名单 + IP 字面量内网判定（含 `::ffff:` hex 归一化）+ 主机名 DNS 解析逐记录判定；**已知残余**：DNS 解析失败放行（离线环境合法主机名不能误杀）、校验后记录变更（DNS 重绑定 TOCTOU）不防 | 重绑定根治需连接期逐包校验，本地单用户场景威胁有限，记录即可 |
| WS 鉴权 | 握手校验 Origin + token（`Sec-WebSocket-Protocol`，`api/ws/validation.ts`） | — |

**日志与错误脱敏（隐私红线）**：

- **日志截断口径**：`truncateLogText` 对原始文本超 500 字符截断并标注（含工具参数 raw、SSE 帧等），三族协议适配器共用同一口径，防超长 raw/上游正文泄入日志（`provider/protocols/shared.ts` truncateLogText、parseToolArgs）

### 9.1 embeddings 内存增长评估与触发条件（P1-5，review M9）

**现状**：sidecar `get_or_load` 把每个 agent 的全部向量驻留内存（`docs` HashMap 与 HNSW 图各持一份，hnsw_rs 的 Point 按值持有数据），无淘汰无上限。磁盘侧已由 P0-5 治理（启动 compaction 重写去重）；M14 起已压缩归档话题的消息向量经 `DeleteDocs` tombstone 删除（docs/doc_ids 移除即不可检索，墓碑行落盘），M47 起孤儿点（重复 upsert 旧点 + 已删文档点）超阈值触发运行期 compaction 物理剔除；P1-5 治理观测——冷载入与每跨 1 万条记录驻留估算日志，≥5 万条升 warn。

**量化**（默认 text-embedding-3-small，1536 维）：

| 指标 | 数值 |
|------|------|
| 每 doc 驻留 | ≈ 13.3KB（向量 6KB × 2 份 + ~1KB 映射/链接开销） |
| 磁盘每行 JSON | ≈ 14KB |
| 索引速率 | 每轮对话的用户与 assistant 消息全部入索引 |
| 中度使用 60 条/天 | ≈ 2.2 万条/年 ≈ 驻留 290MB |
| 重度使用 150 条/天 | ≈ 5.5 万条/年 ≈ 驻留 730MB |
| 10 万条 | ≈ 驻留 1.3GB / 磁盘 1.4GB |

**不设驻留上限的方案评估**：

- **A（内存上限 + LRU 逐出）**：hnsw_rs 不支持删点且 Point 按值持有向量——逐出 `docs` 并不释放图内存；真逐出需重建热图 + 冷数据按需回载并合并结果，改动落在召回路径上，高复杂高风险。
- **B（热冷分层）**：冷侧留磁盘意味着每次 search 解析数百 MB JSON，不可行；冷侧再建索引等于自建向量库，过度设计。
- **C（图/向量分离）**：hnsw_rs 不支持向量与图分离；换支持 mmap 的 usearch 在 P0-5 已因 C++ 工具链风险否决，当前栈不可行。
- **D（监控 + 文档化，所选）**：16GB 内存机器下中度使用 4-5 年、重度约 2 年才到 1.3GB 痛点；观测成本极低，把根治留到规模临近，成本收益最匹配。

**回来做根治的量化触发条件（满足任一即启动）**：

1. 单 agent 文档数 > 100,000（1536 维 ≈ 1.3GB 驻留；sidecar 每跨 1 万条有 info 日志可直接观测，≥5 万条时 warn 已提前报警）
2. `embeddings.jsonl` 单文件 > 1GB
3. sidecar 进程 RSS 观测值 > 2GB
4. 换更高维 embedding 模型（如 3072 维）时按 `docs × (dim×4×2 + 1KB)` 重新折算，上述阈值等比下调

**根治方向预选**：优先评估支持向量外置/mmap 的嵌入式向量库（usearch、sqlite-vec、lancedb），不在 hnsw_rs 上自研 LRU。
| run_command 无沙箱 | 依赖人工审批兜底 | 审批误放行即任意执行 |
