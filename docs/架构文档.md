## 1. 项目定位

CloudMind-Zome 是一个**单用户本地桌面应用**（也可作为 Web 应用运行），核心定位是"多 Agent 协作平台"。

- **单用户**：无登录/注册流程，所有数据本地存储
- **本地优先**：桌面端运行时数据落在 sidecar 解析的统一数据目录（env 优先，Windows 兜底 `%LOCALAPPDATA%\cloudmind-zome`），supervisor 启动 engine 时注入；旧默认目录 `~/.cloudmind-zome` 的数据由 sidecar 启动时一次性迁移。独立 dev（`pnpm dev` 直跑 engine）默认 `~/.cloudmind-zome`。均可用 `CLOUDMIND_DATA_DIR` 覆盖（详见 §6.3）
- **桌面封装**：Tauri 2（Rust + WebView2）。启动链：Tauri → Rust sidecar →（supervisor 守护）→ Node.js 引擎

### 3.2 层间边界

## 4. 核心机制

### 4.1 AgentWorker — 单一数字生命

每个 Agent 对应全局唯一的 `AgentWorker`（`services/engine/src/core/agent-worker.ts`）：

- **一个内部队列** — FIFO 串行处理所有 Jobs
- **一个状态** — `idle` / `busy` / `paused`，由 Worker 单点维护
- **`runTurn()` 调用** — 每轮通过 `services/engine/src/core/react/turn.ts` 执行 ReAct 步骤
- **配置变更联动** — worker 生命周期由 `WorkerRegistry`（`core/worker-registry.ts`，P3-6）单点权威：配置变更经 `retire()` 退役旧 worker（排队 job 显式 settle、在途 turn 排空后才替换，FIFO 串行不变量不破），下次 `getOrCreate` 按新配置懒重建

**Job 类型**：
- 正常对话 — 流式输出 text / thinking / tool_call
- 定时任务 — 由 Scheduler 触发，先持久化用户消息再入队
- Subagent 派发 — `runAgentCollect`，独立 `subagent_<uuid>` sessionId 收集完整输出
- 系统通知 — Subagent 终态经 `enqueueSystemNotice` 注入的 `[系统通知]` 感知回合（通用注入通道；产出写历史；开关 `subagentNotify` 缺省开；notified 幂等）——Intermind inbox 地基

### 4.2 ReAct 循环

```
用户消息 → ContextPipeline.assemble 组装 → LLM 流式调用 → 解析响应
                                                        ↓
                                              ┌─────────┴─────────┐
                                              ↓                   ↓
                                        [普通回复]           [Tool Calls]
                                              ↓                   ↓
                                        保存并结束        执行工具 → 结果加入消息
                                                                    ↓
                                                            继续下一轮 LLM
```

- 单轮最多 **5 步**（maxSteps），超限截断
- **流式事件**（`LLMEvent`，`provider/types.ts`）：
  - `thinking.delta` — 推理内容（折叠显示）
  - `text.delta` — 正文内容
  - `tool.call` — 工具调用
  - `tool.result` — 工具执行结果
  - `step.end` — 单步结束（每个 ReAct step 都发，tool_use 时循环继续）
  - `turn.end` — 一轮结束（ReAct 循环退出后由 runTurn 发出；前端只在此时复位"生成中"状态）

### 4.3 ContextPipeline — L1–L6 分层组装（Phase 1–3、5–7 已完成）

`ContextPipeline`（`services/engine/src/context/pipeline.ts`）在每轮 LLM 调用前组装上下文（`core/react/turn.ts` 接入），预算默认 `maxContextTokens=80000`、`reserveRatio=0.1`（可按 Agent 配置，`core/pipeline-factory.ts`）。

| 层级 | 内容 | 降级策略 |
|------|------|----------|
| L1 | 人格系统提示（SOUL.md + 安全准则 + 技能纪律与技能目录——目录仅名字+一句话，正文经 skill 工具按需取回；`src/mind/mind-files.ts`、`core/agent-worker.ts`） | 不降级 |
| L2 | @提及提醒 | 不降级 |
| L3 | Hot Context（当前会话近期消息） | keep-15 → keep-10 → keep-5 截断 |
| L4 | 语义检索结果（`SemanticMemory[]`，score 降序；经 recall 自然化为伪装 user 历史消息，见下） | keep-10 → 5 → 3 → 丢弃（保留高相关） |
| L5 | 话题摘要（最近压缩档，时间倒序；同经 recall 自然化） | drop-oldest 逐条丢弃最旧 |
| L6-core | 核心工具描述 | 不降级 |
| L6-ext | 扩展工具描述 | halve → 丢弃（当前无扩展工具） |

MIND.md 经验检索（`src/mind/mind-files.ts`，Phase 6 框架）不占独立层级：每轮按当前用户输入做规则版检索（关键词/bigram 匹配 `##` 分块，上限 3 块），命中时伪装成一条 assistant 历史消息注入 L3 之后；不参与降级与多轮去重。SOUL.md/MIND.md 位于 `agents/{agentId}/`，新建 Agent 时生成默认文件。

MIND.md 经验自动沉淀（Phase 7）：话题压缩落档时，同一次压缩 LLM 调用额外输出 0-N 条经验（颗粒度为经验/教训/偏好，非事实流水账），`appendMindExperiences` 以 append-only 方式写入 MIND.md（每块带 frontmatter：source/created/confidence，≤ 0.5 不落盘；双重门槛去重——标题整体 token Jaccard ≥ 0.6 且主体段有共享 token，才并入已有块追加一行补充，绝不原地改写或删除）；frontmatter 仅审计用，不进检索打分与注入消息。

**降级顺序：L5 → L4 → L6-ext → L3**（`context/layers.ts` `DOWNGRADE_ORDER`）。

- Token 计数：`@dqbd/tiktoken` cl100k_base，每条消息 +4 overhead，与 provider 实际发送内容对齐（id/createdAt 不计入）
- 工具结果截断：单条上限 = 预算 × 20%（兜底 16000 tokens），保留头尾（`context/truncate.ts`）
- 截断时清理失去前置 assistant toolCalls 的孤儿 tool 消息，避免 provider 400
- L1.5（平台能力层）曾短暂存在，已于 2026-07-21 移除（commit `ba7f726`）

**L5 话题压缩（Phase 2，`src/memory/topic/`）**：

- **检测**（`detector.ts`，规则版）：显式切换词 / 时间间隔超窗（默认 30 分钟）/ 消息数达阈值（默认 20 条）→ 关闭当前话题；关键词/语义边界留待后续
- **压缩**（`compressor.ts`）：LLM 单程生成「话题主题 + 关键结论」，60s 超时，解析失败走原文兜底；压缩模型可用 `compressionModel` 指定（缺省主模型，失败不 fallback）
- **归档**：压缩档落盘 `_compressed/{topicId}.md`（frontmatter + Summary + Key Points + 原文 msg_ids）；原始消息先写入 `messages_archived.jsonl` 再从热存储移除（`IMessageRepository.archiveAndRemove`，可经 `getArchivedByIds` 恢复）；短话题（<4 条）不调 LLM 仅归档（`archiveOnly`）
- **用户可见完整历史**：聊天接口 `GET /chat/:agentId/messages` 跨存储读取热存储 + 归档（`listBySessionWithArchived`，按 createdAt 归并、limit/before 真分页）——用户看的聊天记录不因压缩消失；她的上下文（L1-L6 组装 / L4 的 archivedMessageIds 排除 / reconcile / 压缩）仍只走热存储，不受影响
- **注入**：每轮组装时取最近 `hotMemoryCount`（默认 2）个压缩档的结构化条目（`latestSummaries`），经 recall 自然化注入（见下）
- **后台队列**（`queue.ts`）：串行 fire-and-forget；归档失败时隔离已写压缩档，避免"摘要+原文"重复注入
- **启动对账**（`memory/reconcile.ts`）：engine 启动时对每个 agent 做三件事——补归档"压缩档已写入但 archiveAndRemove 未完成"的孤儿消息（`reconcileHotStorage`）、收"已关闭已入队未压缩"的 pending 段（`reconcilePendingSegments`）、**跳过开放话题**（`reconcileOrphanedTopic`，真机 #10 方案 2）：退出时仍未关闭的话题原样保留在 topic-state.json，由运行时 TopicTracker 在阈值/显式切换词/时间窗超时自然收——重启是"睡一觉"不是"话题屠杀"；`ZOME_STARTUP_RECONCILE=false` 可关闭

**L4 语义检索（Phase 3，`context/semantic.ts`）**：

- `SemanticRetriever`：候选放大 2 倍 → 当前历史去重 → 已压缩话题原文排除（读压缩档 msg_ids，不读归档全文）→ 相似度 × 分段时间衰减（<7d 1.0 / <30d 0.8 / <90d 0.5 / 保底 0.3）→ `semanticMinScore` 过滤 → `semanticTopK`（默认 10）；检索侧单条文本按 2000 字符截断（`MAX_INJECT_CHARS`，与索引侧一致）
- sidecar 原始返回为**距离**（`1-cosine`），`MemoryIndexer.search` 出口统一换算为相似度
- 压缩档 msg_ids 汇总（`archivedMessageIds`）按档缓存，(mtimeMs, size) 指纹失效，L4 检索与启动对账复用，不再每轮全量读 `_compressed/*.md`

**L4/L5 注入（Phase 5 记忆自然化，`context/recall.ts` + `assembler.ts`）**：

- 不以 system 元信息注入，而是改写为第三人称、带原始时间戳的**伪装 user 历史消息**，与 L3 真实历史按 createdAt 归并穿插（`assembler.ts`）；L1/L2 保持相邻固定前缀（缓存友好）
- 置信度三档（`classifyScore`）：score > 0.7 正常注入；(0.5, 0.7] 模糊化（"好像提到过…这段记忆有些模糊"）；≤ 0.5 丢弃——pipeline 层的 `CONFIDENCE_DROP` 过滤是 `semanticMinScore` 之外的额外门槛
- 单条注入上限 **500 字符**（`MAX_MEMORY_CHARS`，超出摘要化：保留首尾、标注中段省略字数）；2000 字符上限只在检索/索引侧，不是注入上限
- 跨场景命中自然化标注"在另一个对话里"（旧的 `[来自: sessionId]` 标注已移除）
- 时间真实：正文渲染 `[YYYY-MM-DD HH:mm · N天前]`，伪装消息 createdAt 保留原始时间戳
- 多轮去重：同会话（sourceId）已注入条目 id 记录跳过（64 会话 FIFO）；检索失败不伪装，尾随 system 消息明确告知（`retrievalFailedMessage`）
- 规程自动恢复（skillRestore 通道，阶段 5 二期）：最近一条 L5 摘要 frontmatter 记 `usedSkills` 时，组装经 skillService 重取这些技能正文，以尾部独立 system 消息注入（不碰 L1 固定前缀；声明「规程数据、安全准则优先」；单技能截 4000 / 总量截 8000；取失败静默跳过；保护期 = 该摘要为最新 L5 的窗口）

**Agent 级配置**（`packages/shared` `AgentConfig`，bootstrap 逐项透传）：`maxContextTokens`、`compressionModel`、`topicDetectionWindowMinutes`、`topicMessageThreshold`、`semanticSearchEnabled`（同时门控检索与索引）、`semanticTopK`、`semanticMinScore`。非法取值在引擎侧 clamp 并 warn。

│  - message.ts   → agents/<id>/messages.jsonl │
│  - memory.ts    → agents/<id>/memories.jsonl │
│  - action.ts    → agents/<id>/actions.jsonl  │
│  - llm-call.ts  → agents/<id>/llm_calls.jsonl│
├─────────────────────────────────────────────┤
│  MemoryIndexer（memory/indexer.ts）          │
│  - embed：OpenAI SDK embedder（5s 超时包装） │
│  - upsert/search：sidecar gRPC（HNSW）       │
│  - sidecar 不可用时整体静默跳过              │
└─────────────────────────────────────────────┘
```

**数据目录（消息双轨）**：热存储 `messages.jsonl` 之外，话题压缩把原文归档进 `messages_archived.jsonl`；用户可见的聊天接口（`GET /chat/:agentId/messages`）跨存储读取两者（`listBySessionWithArchived`，按 createdAt 归并、limit/before 真分页）——用户看的完整历史不因压缩消失；她的上下文（L1-L6 组装 / L4 的 archivedMessageIds 排除 / reconcile / 压缩）仍只走热存储，不受影响。

**跨会话语义检索**：已实现为 ContextPipeline 的 L4 层（`context/semantic.ts` 的 `SemanticRetriever`，见 §4.3）——embedder + sidecar HNSW 由 `MemoryIndexer` 承载，检索结果经 pipeline 注入、参与预算与降级；sidecar 不可用时静默降级为空。

**全部信任开关（`AgentConfig.trustAllTools`）**：agent 级开关，缺省 `false`（安全默认）。开启后该 agent 的需审批工具在**有审批通道**时自动批准（含不可免问五工具——用户明确信任即放行，这正是开关的意义），不再询问前端；每次自动放行写审计事件 `trusted-auto-approve`（工具名 + 参数摘要，沿用既有脱敏）——用户主权最终体现，审计留痕。无审批通道的路径（定时任务、蓝图、无桥接 subagent/后台傀儡）不受开关影响，仍 fail-closed 拒绝，防止静默越权。

**Puppet 型号库**（`subagent/puppet-models.ts`）：型号 = 命名预设包（`{ name, description, personaSnippet, suggestedTools? }`）。内置四型号（规划师/码农/调研员/审查员，代码常量）；自定义走 `DATA_DIR/puppet-models/*.json`（每型号一文件，zod 字段校验，坏文件跳过 warn，缺失目录按空），同名自定义覆盖内置并 warn（用户主权）。`dispatch_subagent` 的 `kind=puppet` 可选 `puppetModel`：persona 片段拼入傀儡基础设定（不改变傀儡制语义——仍无 SOUL/无 MIND）；`suggestedTools` 有值时傀儡最终工具 = 调用方 agent 白名单 ∩ 型号推荐（只窄化绝不扩权，交集为空拒绝派遣并明确报错）；型号不存在返回明确错误并列出可用型号。只读端点 `GET /puppet-models`（每项带 `source: builtin/custom`），第一版无 CRUD 写端点。

**写入限制**：写入工具通过路径解析限制只能写入工作区 `files/` 子目录（code 模式为 projectRoot 内），并保护 `agent.json`、`messages.jsonl`、`config.json`、`.master-key` 等关键文件。

**MCP 工具**（`tools/mcp/`）：`DATA_DIR/mcp-servers.json` 配置 stdio server，engine 启动连接（单 server 失败降级不阻塞整体）；每个 MCP tool 包装为 `mcp__<server>__<tool>` 命名工具（白名单字符 + 下划线折叠，64 字符封顶 FNV-1a 哈希后缀；同名冲突跳过记 warn），与内置工具同管线注入。审批 fail-closed：仅 `readOnlyHint===true` 免审批；`toolOverrides` 按限定名覆盖（显式免审批 / 强制审批 / `allowRemember` 放行——`mcp__` 前缀默认禁「本会话免问」）。调用失败自愈封顶一次（ping 探活分流 + single-flight 重连后重试，at-least-once 取舍）；server 断线工具保注册（调用时重连）。Windows 经 shim 启动并清理进程树。

## 5. 通信架构

### 5.1 WebSocket 协议

两条路径（均无 `/api/v1` 前缀）：

- `GET /ws/:agentId?sessionId=xxx` — 私聊（`handler.ts`，sessionId 缺省 `"default"`）
- `GET /ws/sessions/:sessionId` — 群聊/会话（`session-handler.ts`）

**Client → Server**：
- `{ "text": "..." }` — 聊天消息（**无 type 字段**，最长 10000 字符）
- `tool.approval` — 审批回执（`approvalId` / `approved` / `remember`；remember 对 `NO_REMEMBER_TOOLS` 五工具无效，见 §4.5）
- `session.set_mode` — 切换 chat / code 模式（仅会话 WS，可带 `projectId`）
- 未知 type 帧静默忽略

**Server → Client**：
- `text.delta` / `thinking.delta` — 流式正文 / 推理
- `tool.call` / `tool.result` — 工具调用与执行结果
- `step.end` — ReAct 单步结束
- `tool.approval_request` — 审批请求（60s 未回视为拒绝）
- `session.mode_changed` — 模式切换确认
- `error` — 错误

握手校验 Origin（`api/ws/validation.ts`，防 CSWSH；无 Origin 的非浏览器客户端放行，Tauri 协议特判，`NODE_ENV=e2e` 全放行）。

### 5.2 群聊路由

```
用户消息
    │
    ▼
┌─────────────────────┐
│ Conductor           │
│ - @mention 精确路由  │（按成员 id 或 name 匹配）
│ - @all / @所有人     │ → 广播

### 5.3 心智互聊 (Intermind)

已实现一期（人形间私信）：`send_private_message` 工具写信——邮箱对称双写（接收方 `intermind:<fromAgentId>` 来信线程 + 发送方 `intermind:<toAgentId>` 来往线程留底），信到后经 `enqueueSystemNotice` 触发接收方一轮感知回合（通知文本「【来自 {name} 的私信】{摘要}」，sourceId 独立 notice 会话）；感知回合带 `intermindRide` 标记，回信只入队不再次唤醒（搭车）。通知摘要截断（200 字）时追加读全文指引，接收方可用 `read_private_messages`（`from: {senderId}`）从自己信箱取完整来往信件（免审批、需白名单授权、傀儡硬禁）。防连环唤醒三防线：搭车标记 + 感知回合无审批通道（写类/派发 fail-closed，无法在感知回合内再派分身）+ 傀儡上下文硬拒。REST 只读：`GET /agents/:id/intermind`、`GET /agents/:id/intermind/:peerId/messages`。设计文档：`docs/design/intermind.md`。待办：免打扰开关、前端 UI、`sessions.jsonl` 显式会话记录。

## 7. 错误处理与恢复

### 7.1 现状

- **LLM 调用韧性层**：错误分类重试（429/5xx/网络/超时指数退避，流式调用仅首事件前重试保安全）+ Agent 级 `fallbackProviderIds` 降级链 + `requestTimeout`/`maxRetries` 消费（`provider/resilient*.ts`）

- 单轮 ReAct 最多 5 步（maxSteps）硬截断
- ContextPipeline 预算降级（见 §4.3）防止超窗口
- 工具结果按预算 20% 截断，防止单条大结果击穿窗口

## 8. 安全模型

> CloudMind-Zome 是**单用户本地应用**，engine 绑定 `127.0.0.1`；REST 全局 Bearer 鉴权（P0-2：除 `/health`、`/ws/*` 外全部端点含 `/docs` 要求 `Authorization: Bearer <token>`——32 字节随机 token 落盘 `DATA_DIR/auth-token`（0600），`CLOUDMIND_AUTH_TOKEN` 可覆盖，常量时间比较），WS 握手 token 走 `Sec-WebSocket-Protocol` + Origin 白名单（防 CSWSH，违规 4401/4403）。以下针对本地桌面场景。

| 风险 | 现状 | 建议 |
|------|------|------|
| 单用户无隔离 | 无多用户支持，所有 Agent 共享同一用户上下文 | 如需多用户需整体扩展 |
| 文件系统逃逸 | `write_file` 限制在 `files/` 子目录；路径校验为纯词法比较，**symlink 可逃逸** projectRoot | 增加 realpath 校验或 chroot |
| 代码执行 | `run_command` 为**无沙箱**任意 shell（`bash` 工具是白名单）；写类工具与 dispatch_subagent 全部接入人工审批，`run_command`/`write_file`/`edit_file`/`dispatch_subagent` 每次必问（不可免问） | 蓝图/定时任务等非交互路径一律拒绝危险工具（已实现） |
| API Key 存储 | `config.json` 中 AES-256-GCM 加密（`services/engine/src/config/crypto.ts`） | 通过 `CLOUDMIND_MASTER_KEY` 覆盖主密钥 |
| SSRF 防护 | Provider `baseUrl` 已校验，但可被 `[::ffff:7f00:1]` 等 hex 形式绕过，且不防 DNS 重绑定 | 完善 IP 段覆盖与 DNS 解析校验 |
| WS 鉴权 | 握手校验 Origin + token（`Sec-WebSocket-Protocol`，`api/ws/validation.ts`） | — |

## 9. 已知限制

| 限制 | 现状 | 影响 |
|------|------|------|
| 消息全量加载 | 无分页，历史全量读入 | 长期对话可能卡顿 |
| sidecar 可选 | 不可用时向量记忆静默降级 | 无语义检索但对话正常 |
| HNSW 索引 | 全量驻留内存 + 增量持久化（P0-5 增量插入/启动 compaction；P1-5 驻留估算监控） | 无驻留上限，根治触发条件见 §9.1 |

### 9.1 embeddings 内存增长评估与触发条件（P1-5，review M9）

**现状**：sidecar `get_or_load` 把每个 agent 的全部向量驻留内存（`docs` HashMap 与 HNSW 图各持一份，hnsw_rs 的 Point 按值持有数据），无淘汰无上限。磁盘侧已由 P0-5 治理（启动 compaction 重写去重）；P1-5 治理观测——冷载入与每跨 1 万条记录驻留估算日志，≥5 万条升 warn。

**量化**（默认 text-embedding-3-small，1536 维）：

| 指标 | 数值 |
|------|------|
| 每 doc 驻留 | ≈ 13.3KB（向量 6KB × 2 份 + ~1KB 映射/链接开销） |
| 磁盘每行 JSON | ≈ 14KB |
| 索引速率 | 每轮对话的用户与 assistant 消息全部入索引 |
| 中度使用 60 条/天 | ≈ 2.2 万条/年 ≈ 驻留 290MB |
| 重度使用 150 条/天 | ≈ 5.5 万条/年 ≈ 驻留 730MB |
| 10 万条 | ≈ 驻留 1.3GB / 磁盘 1.4GB |

**不设驻留上限的方案评估**：

- **A（内存上限 + LRU 逐出）**：hnsw_rs 不支持删点且 Point 按值持有向量——逐出 `docs` 并不释放图内存；真逐出需重建热图 + 冷数据按需回载并合并结果，改动落在召回路径上，高复杂高风险。
- **B（热冷分层）**：冷侧留磁盘意味着每次 search 解析数百 MB JSON，不可行；冷侧再建索引等于自建向量库，过度设计。
- **C（图/向量分离）**：hnsw_rs 不支持向量与图分离；换支持 mmap 的 usearch 在 P0-5 已因 C++ 工具链风险否决，当前栈不可行。
- **D（监控 + 文档化，所选）**：桌面 16GB 下中度使用 4-5 年、重度约 2 年才到 1.3GB 痛点；观测成本极低，把根治留到规模临近，成本收益最匹配。

**回来做根治的量化触发条件（满足任一即启动）**：

1. 单 agent 文档数 > 100,000（1536 维 ≈ 1.3GB 驻留；sidecar 每跨 1 万条有 info 日志可直接观测，≥5 万条时 warn 已提前报警）
2. `embeddings.jsonl` 单文件 > 1GB
3. sidecar 进程 RSS 观测值 > 2GB
4. 换更高维 embedding 模型（如 3072 维）时按 `docs × (dim×4×2 + 1KB)` 重新折算，上述阈值等比下调

**根治方向预选**：优先评估支持向量外置/mmap 的嵌入式向量库（usearch、sqlite-vec、lancedb），不在 hnsw_rs 上自研 LRU。
| run_command 无沙箱 | 依赖人工审批兜底 | 审批误放行即任意执行 |
