# CloudMind-Zome 开发指南

> 版本：2.2 | 日期：2026-08-11
> 面向开发者的快速上手和调试指南。

## 1. 环境准备

### 1.1 要求与技术栈

**运行要求**：
- Node.js 22+
- Rust（版本见 `rust-toolchain.toml`，当前 1.88）
- protoc 27+

**技术栈**：
- 后端：Node.js 22 + Fastify 5
- 前端：Nuxt 3 + Vue 3 + Pinia + TypeScript
- 桌面：Tauri 2（Rust + WebView2）
- 侧车：Rust `crates/zome-sidecar`（gRPC）
- 包管理：pnpm workspace + Turborepo

### 1.2 安装依赖

```bash
pnpm install
```

### 1.3 启动开发环境

```bash
# Web 模式（同时启动 engine + web）
pnpm dev

# Tauri 桌面模式（需 Rust）
pnpm --filter @mindcloud/desktop dev
```

服务启动后：
- 前端：`http://localhost:3000`
- 后端 API：`http://127.0.0.1:8848`（Swagger UI：`http://127.0.0.1:8848/docs`）
- WebSocket：`ws://127.0.0.1:8848/ws/:agentId?sessionId=xxx`

> sidecar 在 Web 模式下**不是必需的**：没有它向量记忆会静默降级，其余功能正常。桌面模式由 Tauri 自动拉起 sidecar，sidecar 再守护 engine。

> **Web 开发模式 engine 鉴权零配置**：nuxt dev server 读取 engine 数据目录的 `auth-token` 文件（`CLOUDMIND_DATA_DIR`，缺省 `~/.cloudmind-zome`），经 `/api/engine-token` 在运行时下发给浏览器，无需手动配置。`NUXT_PUBLIC_ENGINE_TOKEN` 或 `localStorage["cloudmind.engineToken"]` 仍是更高优先级的显式覆盖（仅开发需要时使用）；该自动通道只存在于本地开发（localhost），生产/静态构建不暴露 token。

### 1.4 环境变量

| 变量 | 说明 | 默认值 |
|------|------|--------|
| `CLOUDMIND_DATA_DIR` | 运行时数据目录（配置、Agent 数据） | 独立 dev 默认 `~/.cloudmind-zome`；桌面端由 sidecar 解析注入（Windows 为 `%LOCALAPPDATA%\cloudmind-zome`） |
| `CLOUDMIND_MASTER_KEY` | 用于加密 API Key 的主密钥；若未设置则自动生成 `.master-key` | 自动生成 |
| `ZOME_LOG_LEVEL` | engine 业务日志级别（pino；逐条诊断在 debug 级） | `info` |
| `CLOUDMIND_ALLOWED_ORIGINS` | CORS / WS Origin 白名单，多个用英文逗号分隔 | `http://localhost:3000,http://127.0.0.1:3000,http://localhost:1420` |
| `PORT` | engine HTTP 监听端口 | `8848` |
| `NODE_ENV` | 设为 `e2e` 时使用 Mock provider、CORS/WS Origin 全放行 | — |
| `ZOME_SIDECAR_ADDR` | sidecar gRPC 地址 | `127.0.0.1:50051` |
| `ZOME_PROTO_PATH` | zome.proto 路径覆盖 | 向上找 `crates/zome-sidecar/proto/zome.proto` |
| `ZOME_STARTUP_RECONCILE` | 启动对账（补归档热存储孤儿消息）；`false` 关闭 | `true` |
| `NUXT_PUBLIC_ENGINE_TOKEN` | web 开发显式覆盖 engine token（缺省自动从 `CLOUDMIND_DATA_DIR/auth-token` 读取，无需配置） | 自动读取 |

sidecar（Rust）侧另有：`ZOME_MASTER_KEY`（sidecar 加密密钥，注意与 engine 不是同一套）、`ZOME_NODE_PATH`、`ZOME_ENGINE_ENTRY`。

## 4. 调试技巧

### 4.1 查看日志

- engine 业务日志统一经 `src/logger.ts`（pino）输出：stdout + 内存环形缓冲多流，可通过 `GET /logs` 或前端 LogPanel 查看；级别由 `ZOME_LOG_LEVEL` 控制（默认 info，逐条诊断在 debug 级）
- 关键日志标记：
  - `[worker] 创建 worker` / `[worker] 配置变更：退役旧 worker` — worker 生命周期（WorkerRegistry）
  - `[reconcile] agent=...` — 启动对账（补归档/补压缩）
  - `[topic] ...` — 话题压缩/状态落盘类 warn
  - `scheduler tick failed` — 调度轮询错误（带节流计数）

### 4.2 查看 WebSocket 流量

浏览器 DevTools → Network → WS → 选择 `ws://127.0.0.1:8848/ws/...`

常见帧：
- 发送 `{ "text": "..." }` → 收到 `text.delta` / `thinking.delta` / `tool.call` / `tool.result` / `step.end`
- 审批：`tool.approval_request` → 回复 `tool.approval`

### 4.3 检查 per-Agent 存储

```bash
# 独立 dev 的数据目录为 ~/.cloudmind-zome；桌面端为 sidecar 解析目录
# （Windows: %LOCALAPPDATA%\cloudmind-zome）
ls ~/.cloudmind-zome/agents
# 每个 Agent 对应一个目录，内含 agent.json、messages.jsonl、memories.jsonl 等
```

### 4.4 DSML 探针：实测协议族工具调用率

`scripts/dsml-probe.mts`（631d09f 留档、8c3de97 更新）：复用 engine 的 provider 配置（`ConfigRepository` 读首条 provider）+ `OpenAIResponsesProvider` 适配器，带 recall 工具定义对 `deepseek-v4-flash` 连打 10 次流式调用，统计「标准 tool.call / DSML 文本 / 两者皆无」的分布（dsml-probe.mts:5-12,42-62）。历史构造模拟真机长上下文——15 轮对话 + 工具调用交互约 4K tokens（dsml-probe.mts:25-41）。

```bash
pnpm --filter @mindcloud/engine exec tsx ../../scripts/dsml-probe.mts
```

> 探针直连真实上游（有计费），不经 worker / record-calls，不落 llm_calls。切换协议族对比时改文件顶部 import 的适配器即可（当前固定 Responses，dsml-probe.mts:3,12）。实证结论见 commit 8c3de97：DeepSeek `/responses` 端点 10/10 结构化工具调用零 DSML——这正是 per-model apiMode（flash 走 responses）的依据。

## 5. 常见开发任务

### 5.1 添加新工具

1. 在 `services/engine/src/tools/builtin/` 下创建新文件
2. 实现 `Tool` 对象（定义名称、描述、Zod schema、execute 函数）
3. 在 `services/engine/src/tools/builtin/index.ts` 注册到内置工具列表

示例：
```typescript
import type { Tool, ToolContext, ToolResult } from "../types.js";
import { z } from "zod";

const parameters = z.object({ param: z.string() });

export const myTool: Tool = {
  name: "my_tool",
  description: "...",
  parameters,
  accesses: [{ resource: "file", action: "read" }], // resource: file | network | process | memory
  async execute(ctx: ToolContext, args: unknown): Promise<ToolResult> {
    const { param } = args as { param: string };
    return { success: true, output: `Result: ${param}` };
  },
};
```

> 写类/危险工具加 `requiresApproval: true`：交互式会话中需人工确认，无审批通道的调用方（定时任务、蓝图、subagent）会被自动拒绝。

### 5.2 修改 Agent 配置字段

Agent 类型在 `packages/shared/src/index.ts`（`AgentConfig`）。新增字段后：

1. 在相关 repository 中处理序列化/反序列化
2. 在 `apps/web/components/agent-edit/*.vue`（编辑器为 `AgentEditor.vue`）中添加对应 UI
3. 更新测试

> 例外：引擎侧消费的高级字段可不加 UI——`compressionModel` / `topicDetectionWindowMinutes` / `topicMessageThreshold` / `semanticSearchEnabled` / `semanticTopK` / `semanticMinScore` 目前仅在 `bootstrap.ts` 逐项透传（判空，同 `maxContextTokens` 模式），经 REST 直接写入 agent.json 生效。改 shared 后记得 `pnpm --filter @mindcloud/shared build`（engine/web 引用的是 dist）。

### 5.3 ContextPipeline 与话题压缩

- 管线本体：`services/engine/src/context/`（`pipeline.ts` 组装循环、`layers.ts` 层定义、`downgrade.ts` 降级步骤、`assembler.ts` 渲染、`semantic.ts` L4 检索器）
- 话题压缩：`services/engine/src/memory/topic/`（`detector.ts` 边界检测、`tracker.ts` 话题跟踪、`compressor.ts` LLM 压缩、`store.ts` `_compressed/` 读写、`queue.ts` 后台队列）
- 启动对账：`services/engine/src/memory/reconcile.ts`（engine 启动时补归档"压缩档已写但归档未完成"的孤儿消息，`ZOME_STARTUP_RECONCILE=false` 关闭）
- 接线点：`services/engine/src/core/agent-worker.ts`（processQueue 内的检测/注入/归档触发）
- 新增/调整降级步骤：改 `downgrade.ts` 的步骤数组（顺序即 L5 → L4 → L6-ext → L3），并补 `tests/context/downgrade.test.ts` 的序列断言
- 相关测试：`tests/context/`（管线/检索）、`tests/topic/`（检测/压缩/落盘）、`tests/core/agent-worker.test.ts`（集成）

> 注意 score 语义：sidecar 返回**距离**（1-cosine），相似度换算统一在 `MemoryIndexer.search` 出口，下游不要直接消费 sidecar 原始 score。

### 5.4 修改 ReAct 循环

- `services/engine/src/core/react/turn.ts` — `runTurn()` 主入口（每轮先 `ContextPipeline.assemble`）
- `services/engine/src/core/react/step.ts` — 单步执行

修改后需验证：
- 私聊正常输出
- 工具调用正常返回
- 循环能正确终止
- 超预算时降级路径正确（`services/engine/tests/context/`）

### 5.5 新增 API 端点

1. 在 `services/engine/src/api/routes/` 下创建或修改路由文件。
2. 使用 Fastify 的 `schema` 选项添加 `summary` 和 `tags`，Swagger 会自动收录。
3. 在 `services/engine/src/api/server.ts` 中调用 `registerXxxRoutes(app, context)`。
4. 在 `services/engine/tests/api/` 添加对应集成测试。

示例：

1. 在 `apps/web/components/` 创建 `.vue` 组件。

### 6.2 测试惯例增补（2026-08-11）

- **行为级断言优于存在性断言**（598a1a1 复审确立）：断言状态机/输出行为，不断言「某函数被调用过」。范式见 `services/engine/tests/handoff/arbitration.test.ts:1-8`——V1–V5 仲裁场景驱动真实 manager/loop/registry，断言最终状态与事件序列。
- **同模式横向扫描义务**：修一类缺陷时 grep 同模式的其他文件一并排查。教训：2db9f4c A3 给 `handoff-state.json` 加了损坏隔离（`services/engine/src/handoff/state.ts:25-47`），同模式的 `topic-state.json` 漏网——它经 `DocumentStore.readJson` 读取，JSON 损坏直接上抛（`services/engine/src/memory/document-store.ts:81-84`、`services/engine/src/memory/topic/state.ts:95-97`），已入路线图二期欠账。
- **turbo 偶发 flaky 复跑即绿不算失败**：全量测试偶发 tinypool `ERR_IPC_CHANNEL_CLOSED` 中止，复跑即绿，属基础设施性不稳定（`docs/reviews/2026-07-27-p2-阶段review.md:153,193`）；复跑仍红才按真失败排查。

## 8. 隐私红线与仲裁面准则（2026-08-11 增补）

### 8.1 隐私红线规范

日志落盘与对外错误响应的统一口径（2db9f4c A2 确立，324206c F2/F3 补齐到三协议族同口径）：

1. **raw 一律截 500 并标注**：SSE 帧、流式工具参数等原始文本经 `truncateLogText`（`services/engine/src/provider/protocols/shared.ts:280-283`，超 500 字符截断并标注「已截断 N 字符」）；三个协议族同一出口——`openai-responses.ts:226`、`anthropic-messages.ts:230`、`openai-compatible-chat.ts:142-145`。
2. **错误消息不落上游回显原文**：test-connection 失败只落 `describeUpstreamError` 的固定分类文案 + status/kind + 标识字段（文案表 `services/engine/src/api/routes/compute.ts:154-178`，日志字段 `compute.ts:430-439`），客户端 502 响应同口径（`compute.ts:440`）——上游错误体常把 Authorization/密钥回显进 message，原文进日志即泄密。Provider 对象对外输出经 `sanitizeProvider` 把 apiKey 改写为 `"***"`（`compute.ts:180-182`）。
3. **脏帧只打 type**：WS 下发前 `sanitizeDeltaEvent` 丢弃非 string delta 的帧，warn 只带 `eventType`，不落整事件（脏 delta 可能携带超长/敏感负载，`services/engine/src/api/ws/validation.ts:71-84`）。
4. **llm_calls 只记账目字段**：`LLMCallRecord` 仅含 id / agentId / provider / providerId / model / 三档 token / durationMs / status / error / createdAt（`services/engine/src/plugins/llm/record-calls.ts:65-78`），不含 prompt 与正文；落盘 fire-and-forget，失败仅 warn 不影响主链路（`record-calls.ts:79-81`）。

### 8.2 handoff 仲裁面设计准则

handoff 续跑链是「loop 每连接一份 / record 全局单条目」的不对称结构（`services/engine/src/handoff/registry.ts:3-12`），跨连接共享资源的操作纪律（598a1a1 确立，8341bf7 补 R1/R2）：

1. **跨连接资源操作一律走 registry 仲裁面**：`HandoffLoopRegistry` 按 agent+session 聚合所有连接的 loop，`cancel` 一次完成全局 record 取消 + 全部连接 loop 打断（`registry.ts:42-48`）；断连专用 `cancelConnection`——维度内还有其它活跃链持有者时只取消本连接资源，不触碰全局 record（`registry.ts:62-85`）。禁止直连单个 loop 的 cancel：8341bf7 R2 前 `resume_history_failed` 直连 `loop.cancel` 会漏掉其它连接，现状统一走 `context.handoffLoops.cancel`（`services/engine/src/api/ws/handler.ts:159`；REST DELETE 同入口 `services/engine/src/api/routes/handoff.ts:59`）。
2. **代际识别以 record 持久化 chainId 为权威锚点**：handleBook 只放行与活跃 record chainId 相同的 book，旧链/异链迟到 book 直接拦截（`services/engine/src/handoff/resume-loop.ts:87-107`）；startResume 调度前复核 record/loop 代际与控制面权威一致（`resume-loop.ts:156-181`）；onJobDone 双重复核，旧链迟到完成 warn 记档不转移（`resume-loop.ts:217-255`）。chainId 随 record 落盘（598a1a1），重启后闩锁权威不丢；各 loop 本地 `currentChainId` 只是兼容迁移期的兜底比对（`resume-loop.ts:100-107`）。
3. **浮空 Promise 禁令**：fire-and-forget 的 void 调用必须带 `.catch`——WS 消息串行链 `chain.then(...).catch(...)`（`handler.ts:73`）、`void handoffLoop.onJobDone(...).catch(doneErr => ...)`（`handler.ts:143-153`）、`sink.append(record).catch(...)`（`record-calls.ts:79-81`）；resume-loop 内部所有异步状态转移 try/catch 记档不 throw（`resume-loop.ts:217-281`）。浮空 reject 在 Node 里是进程级事故。
