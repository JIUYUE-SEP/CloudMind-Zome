## P4-1 业务日志接入 pino（e4cf1d6，对应 O-B1）

**原问题**：pino→环形缓冲→/logs→LogPanel 管道齐全，但业务日志全是裸 console（基线记 52 处/18 文件），LogPanel 只剩 Fastify 请求日志。

**修复方案**：新增 `services/engine/src/logger.ts` 统一出口（pino multistream：stdout + 环形缓冲共享流，`ZOME_LOG_LEVEL` 控级别，默认 info），全部 console 改写为 logger，server.ts 的 Fastify logger 复用同一流。

**验证结果：真的修好**

- 清零属实：`grep -rn "console\." services/engine/src` 当前 0 匹配（tests 目录剩 3 处均为测试内容本身，非业务日志）。
- 级别语义不是懒做法：`agent-worker.ts` 逐条诊断（enqueue/processQueue/tools 数量）降 `logger.debug`（`core/agent-worker.ts:135,137,323,333`），torn JSONL/读取降级类保持 warn，写盘失败/回调异常保持 error，`logger.ts:12-17` 有明确级别约定注释。
- 关键上下文保留进结构化字段：err 统一 `{ err }` 合并（pino 重载），agentId/sessionId 进字段（如 `api/ws/handler.ts:93,95`）。
- 关键路径补记属实：WS 私聊/群聊连接建立与关闭带 code/reason（`handler.ts:93-95`、`session-handler.ts:131-133`），worker 创建/退役（`core/worker-registry.ts:78,32`）。
- "批量脚本误伤 6 处回滚重做"的最终版未见残留误伤：通读全部 204 insertions 的 diff，改动均限于 console→logger 替换、import、测试 spy 替换，无逻辑改动；687 测试全绿佐证。
- LogPanel 通路有测试佐证：`tests/api/logs.test.ts` 新增用例断言业务 logger 经 /logs 可读、debug 默认不输出（测试通过）。

## P4-2 desktop 日志落盘（13b922c，对应 O-B2）

**原问题**：desktop 形态下 engine 只写 stdout、Tauri tracing 只有 fmt stdout，用户机器上无任何日志文件。

**修复方案**：Tauri 侧 tracing 加 tracing-appender 文件输出（日轮转 + max 7 份，非阻塞写入），位置为数据目录 logs/（env 优先，兜底 `data_local_dir()/cloudmind-zome/logs`）；engine 日志经"engine stdout → sidecar 继承 → Tauri 捕获 → tracing"统一链入档。

**验证结果：真的修好**

- 落盘链路逐环核实：`crates/zome-sidecar/src/supervisor/mod.rs:124` spawn engine 未设 stdio（默认 inherit，engine stdout 进 sidecar stdout）→ `apps/desktop/src-tauri/src/sidecar.rs:43-47` CommandEvent::Stdout/Stderr 逐行喂 tracing → `main.rs` 的 registry 双 layer（stdout + 文件，`with_ansi(false)`）→ 文件。打包形态同样走此链，不依赖 dev 环境。
- 轮转属实：`main.rs` `build_file_writer` 用 `Rotation::DAILY` + `max_log_files(7)`，非无限增长；`tracing_appender::non_blocking` 非阻塞，WorkerGuard 活到 `run()` 返回。
- 降级属实：日志目录不可用时 eprintln 并退化仅 stdout，不阻断启动（`main.rs` 的 let-else 分支）。
- 关键事件覆盖够排查 Failed to fetch：sidecar 拉起/意外退出/spawn 失败（`sidecar.rs:31,34,63-66`）、backend 健康等待超时（`sidecar.rs:106`）、supervisor 健康检查/重启/放弃（`supervisor/mod.rs:165-234` 全程 tracing）都会进文件；engine 的 pino 业务日志（P4-1）也经同一链入档。
- 测试属实：`cargo test` 实跑 6/6 通过，含 log_dir 契约与 file writer 真实写文件两例。

**问题**：无 Blocker/Major。Minor：data_local_dir 失败兜底为 `"."`（CWD 相对路径），日志会写到启动目录，位置不可预期（`main.rs` log_dir）。

## P4-4 scheduler tick 错误节流（5b92ec8，对应 O-M1）

**原问题**：tick 默认 1s 一次，`agentRepository.list()`/`repo.list()` 持续故障时每秒一条 error 无限刷屏（bench-agent 刷屏根因）。基线同条还列了次级风险：agent.ts watcher 反复报错、embedder 挂掉时每条消息一条 warn。

**修复方案**：新增 `scheduler/error-throttle.ts`（首条即记，1s→4s→16s→…→5min 封顶退避，窗口内计数，窗口到一条带 count/suppressed），tick 级与任务级 key 分开，成功时按前缀 recover 记"已恢复"。

**验证结果：部分修好（根因已修，O-M1 条目内次级风险未处理）**

- 节流逻辑核实正确（`error-throttle.ts:44-66`）：首条立即返回、窗口内只计数返回 undefined、窗口到返回累计并重置；退避 ×4 封顶 5min。按 1s tick 推算同错误 4 次 tick 出 2 条，与 commit 声称一致；scheduler 集成测试断言了这一点（通过）。
- 不吞信息：窗口到的一条带 `count`（累计）与 `suppressed`（折叠数）（`scheduler.ts:78-84` logThrottled）；恢复时 tick 级/任务级各记一条"已恢复"带累计（`scheduler.ts:63-65,119-121`）。
- 不同错误分开节流：key = `tick:{msg前120字符}` / `task:{id}:{msg前120字符}`（`scheduler.ts:15-18`），不同任务/原因互不串扰，有单测覆盖。
- 生产行为除节流外不变：diff 限于错误路径，687 全绿。
- **未修部分**：O-M1 同条列出的次级刷屏源原样保留——`memory/repositories/agent.ts:57,62,68` watcher 三处 error 无节流（文件被反复写坏时每次 watch 回调一条），`memory/indexer.ts:47` embedder 挂掉时每条消息一条 warn 无节流。commit message 只声称修 scheduler，未夸大；但 O-M1 作为验收条目只算部分完成。

**问题**：Major-1（次级刷屏源未节流，见下）。Minor：errKey 取错误消息前 120 字符，若消息含动态内容（ID/时间戳/路径）key 会发散导致节流失效，且 `entries` Map 只在 recover 时清除、长期运行有无界增长可能（`error-throttle.ts:32`、`scheduler.ts:16-18`）。

## P4-5 LLM 调用落档接通 LLMCallRepository（966f4dc，对应架构 review 死代码节）

**原问题**：`LLMCallRepository.append()` 全工程零调用方，模型/耗时/token/错误率零记录。

**修复方案**：`provider/record-calls.ts` 装饰器包装 provider，bootstrap getOrCreateWorker 单点接线；OpenAIProvider 加 `stream_options.include_usage`，usage 经 step.end 事件透传；落盘 fire-and-forget。

**验证结果：真的修好（一处未覆盖路径未如实声明，见 Minor）**

- 死代码已接通：`bootstrap.ts:134-138` 包装后注入 worker；worker 主链路（`agent-worker.ts:415`）与压缩（`agent-worker.ts:108`）共用 `this.config.provider`（即包装后实例）；subagent 经 dispatcher 走 worker，同被覆盖。`append()` 有了真实调用方。
- token 用量不硬凑：`llm.ts:56` 加 `stream_options.include_usage`（OpenAI 协议标准参数），`llm.ts:63-68` 收末块 usage，`llm.ts:120` step.end 携带；拿不到不携带、落档记 0（`record-calls.ts:33-34,37-39`）。
- 错误记录验证过一处关键疑点：OpenAIProvider 的 catch 会先把错误以 text.delta 透出但**随后 rethrow**（`llm.ts:121-125` `throw new ProviderError(...)`），装饰器 catch 能拿到，status=error 落档后异常继续上抛（`record-calls.ts:43-46`）——失败不会记成 ok。测试有对应用例（通过）。
- 热路径零阻塞：记录构造在流结束后 finally 中进行，`sink.append(...).catch(warn)` fire-and-forget（`record-calls.ts:47-62`），append 底层是 appendLine 异步写（`llm-call.ts:19-21`），失败仅 warn。
- 增长风险声明属实且留了注释：llm_calls.jsonl 只增，list() 有 100MB 上限，读取侧治理留后续（`llm-call.ts:11-14` 注释，与 commit 声明一致）。
- PlanManager 不接声明属实：`bootstrap.ts:122` 确为裸 provider。

**问题**：无 Blocker/Major。Minor：reconcile 孤儿压缩路径自建裸 provider 未接落档（`bootstrap.ts:296`），commit 声称"压缩全覆盖"只字未提这条路径——属覆盖缺口+声明不全面；`bootstrap.ts:135-139` 新行 6 空格缩进与上下文 4 空格不齐（批量编辑痕迹，无功能影响）。
